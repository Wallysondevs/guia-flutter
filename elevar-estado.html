Flutter Elevando o Estado

Um app é feito de muitos widgets pequenos, e eles precisam conversar. O nome do produto tem de chegar ao cartão do produto; o toque no botão "comprar" tem de chegar ao carrinho, que fica lá no topo da tela. Nesta aula você vai ver os dois caminhos da conversa: dados descem pelo construtor e avisos sobem por funções (os callbacks). E vai aprender a regra que resolve a maioria dos problemas de "como esse widget fica sabendo daquilo?": elevar o estado (em inglês, lifting state up).

Você vai aprender
  • Como passar dados de um widget pai para um filho: parâmetros no construtor.
  • Por que um estado guardado no filho fica "preso" lá dentro.
  • Como elevar o estado para o pai e devolver ao filho só uma função (VoidCallback).
  • Como mandar um valor junto com o aviso (ValueChanged<T>).
  • O erro real de chamar setState num StatelessWidget.

As telas desta aula vieram de um Flutter de verdade, no laboratório da Ana, em tamanho de celular, com fotos antes e depois dos toques.

A ideia: o caderno do caixa

Na lojinha da Ana, cada prateleira tem um funcionário. Se cada um anotar as vendas no próprio caderninho, ninguém sabe o total do dia: o caixa teria de ir de prateleira em prateleira perguntando. O jeito certo é ter um caderno só, no caixa. Os funcionários não anotam nada; eles só avisam o caixa: "vendi um café".

  • O caixa é o pai: guarda o estado (o total).
  • Os funcionários são os filhos: recebem o que precisam mostrar (nome, preço) e recebem um jeito de avisar (a função onComprar).

1. O problema: o estado preso no filho

Na primeira versão, cada ProdutoTile é um StatefulWidget com a sua própria quantidade:

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('Lojinha da Ana')),
        body: const Column(
          children: [
            ProdutoTile(nome: 'Café', preco: 18.90),
            ProdutoTile(nome: 'Pão de forma', preco: 9.50),
            ProdutoTile(nome: 'Manteiga', preco: 12.00),
          ],
        ),
      ),
    );
  }
}

class ProdutoTile extends StatefulWidget {
  const ProdutoTile({super.key, required this.nome, required this.preco});

  final String nome;
  final double preco;

  @override
  State<ProdutoTile> createState() => _ProdutoTileState();
}

class _ProdutoTileState extends State<ProdutoTile> {
  int _quantidade = 0;

  @override
  Widget build(BuildContext context) {
    final valor = widget.preco.toStringAsFixed(2).replaceAll('.', ',');
    return ListTile(
      title: Text(widget.nome),
      subtitle: Text('R\$ $valor · no carrinho: $_quantidade'),
      trailing: IconButton(
        icon: const Icon(Icons.add_shopping_cart),
        tooltip: 'Comprar ${widget.nome}',
        onPressed: () => setState(() => _quantidade++),
      ),
    );
  }
}

Dados descendo: o pai passa o nome e o preço pelo construtor. Dentro do State, eles são lidos com widget.nome e widget.preco (veja StatefulWidget).
int _quantidade = 0;
O estado, guardado em cada produto.

Escreve o preço com duas casas e vírgula: 18,90.
tooltip: 'Comprar ${widget.nome}'
A dica do botão de ícone ("Comprar Café"), que o leitor de tela também fala.

Cada produto conta direitinho: 2 cafés, 0 pães, 1 manteiga. Mas tente mostrar o total no título ou no pé da tela: o MeuApp não tem como saber. Cada _quantidade está trancada dentro do seu _ProdutoTileState, e um widget não consegue ler o estado de outro. É o caderninho em cada prateleira.

2. A solução: elevar o estado para o pai

A regra é: o estado mora no widget mais baixo da árvore que é pai de todos os que precisam dele. Quem precisa do total? O título, o pé da tela e os botões dos três produtos. O pai em comum é a tela inteira, a Loja. Então o estado sobe para ela, e o ProdutoTile vira um StatelessWidget:

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(home: Loja());
  }
}

class Loja extends StatefulWidget {
  const Loja({super.key});

  @override
  State<Loja> createState() => _LojaState();
}

class _LojaState extends State<Loja> {
  int _itens = 0;
  double _total = 0;

  void _comprar(double preco) {
    setState(() {
      _itens++;
      _total += preco;
    });
  }

  @override
  Widget build(BuildContext context) {
    final total = _total.toStringAsFixed(2).replaceAll('.', ',');
    return Scaffold(
      appBar: AppBar(title: Text('Lojinha da Ana · $_itens itens')),
      body: Column(
        children: [
          ProdutoTile(nome: 'Café', preco: 18.90, onComprar: () => _comprar(18.90)),
          ProdutoTile(nome: 'Pão de forma', preco: 9.50, onComprar: () => _comprar(9.50)),
          ProdutoTile(nome: 'Manteiga', preco: 12.00, onComprar: () => _comprar(12.00)),
          const Divider(),
          Text('Total: R\$ $total', style: const TextStyle(fontSize: 24)),
        ],
      ),
    );
  }
}

class ProdutoTile extends StatelessWidget {
  const ProdutoTile({
    super.key,
    required this.nome,
    required this.preco,
    required this.onComprar,
  });

  final String nome;
  final double preco;
  final VoidCallback onComprar;

  @override
  Widget build(BuildContext context) {
    final valor = preco.toStringAsFixed(2).replaceAll('.', ',');
    return ListTile(
      title: Text(nome),
      subtitle: Text('R\$ $valor'),
      trailing: IconButton(
        icon: const Icon(Icons.add_shopping_cart),
        tooltip: 'Comprar $nome',
        onPressed: onComprar,
      ),
    );
  }
}
class _LojaState … int _itens = 0; double _total = 0;
O estado subiu: agora o caderno é um só, na Loja.
void _comprar(double preco)
O único lugar que muda o estado. Recebe o preço, soma um item e soma o preço ao total, num setState.
final VoidCallback onComprar;
No filho, um parâmetro que é uma função. VoidCallback é o nome do Flutter para "uma função sem parâmetros que não devolve nada", o mesmo que void Function(). O filho não sabe o que ela faz; só sabe chamá-la.
onPressed: onComprar
O botão do filho chama a função que veio do pai. É o aviso subindo.
onComprar: () => _comprar(18.90)
No pai, cada produto recebe uma função que chama o _comprar com o preço dele.
appBar: AppBar(title: Text('Lojinha da Ana · $_itens itens'))
Agora o título consegue mostrar o número de itens, porque o estado está no mesmo widget que monta o título. Por isso o Scaffold passou para dentro da Loja.

Os mesmos toques da seção 1, e agora o título mostra 3 itens e o pé da tela, Total: R$ 49,80 (18,90 + 18,90 + 12,00). O caminho de um toque:

  1. A Ana toca no carrinho do Café. O IconButton chama o onComprar que o ProdutoTile recebeu.
  2. Essa função foi criada na Loja: ela chama _comprar(18.90).
  3. O _comprar roda o setState da Loja.
  4. O build da Loja roda de novo e monta o título, os três ProdutoTile e o total, todos com os valores novos.

A árvore, com o caminho dos dados (↓) e dos avisos (↑):

Loja  (estado: _itens, _total)
└─ Scaffold
   ├─ AppBar  ↓ "Lojinha da Ana · 3 itens"
   └─ Column
      ├─ ProdutoTile ↓ nome, preco, onComprar   ↑ onComprar()
      ├─ ProdutoTile ↓ nome, preco, onComprar   ↑ onComprar()
      ├─ ProdutoTile ↓ nome, preco, onComprar   ↑ onComprar()
      └─ Text  ↓ "Total: R$ 49,80"

Missão: nesta versão, os produtos recebem uma função vazia (onComprar: () {}), e o carrinho nunca muda. Ligue cada produto ao caixa: troque cada () {} por uma função que chama o _comprar com o preço do produto, como () => _comprar(18.90). (Pista: o analisador do Dart avisa que o _comprar não é usado em lugar nenhum: The declaration '_comprar' isn't referenced.)

3. Formas diferentes de avisar o pai

O VoidCallback só diz "aconteceu". Quando o filho precisa mandar um valor junto, use ValueChanged<T>, "uma função que recebe um valor do tipo T". Assim, o próprio produto manda o seu preço, e o pai não precisa repetir o número:

// no filho
final ValueChanged<double> onComprar;
…
onPressed: () => onComprar(preco),

// no pai: passa o próprio método, sem parênteses
ProdutoTile(nome: 'Café', preco: 18.90, onComprar: _comprar),

Repare no onComprar: _comprar: como o _comprar já recebe um double, ele mesmo serve de ValueChanged<double>. É o mesmo padrão que os widgets do Flutter usam: o onChanged de um Switch é um ValueChanged<bool>, e o de um TextField, um ValueChanged<String> (aulas Checkbox, Switch e Radio e Campos de Texto).

TipoÉ o mesmo queUse quando
VoidCallbackvoid Function()O filho só avisa que algo aconteceu (um toque)
ValueChanged<T>void Function(T valor)O filho manda um valor junto (o preço, o texto digitado)
void Function(String nome, int qtd)—Vários valores (ou mande um objeto)

E quando o estado precisa ser lido por widgets muito longe uns dos outros (a tela do carrinho e a tela de pagamento), passar funções de pai para filho para neto fica cansativo. Para isso existem o InheritedWidget e o Provider, no nível 3.

Quando dá errado

Chamou setState dentro do filho StatelessWidget 
      trailing: IconButton(
        icon: const Icon(Icons.add_shopping_cart),
        tooltip: 'Comprar $nome',
        onPressed: () => setState(() {}),
      ),
lib/main.dart:71:26: Error: The method 'setState' isn't defined for the type 'ProdutoTile'.
 - 'ProdutoTile' is from 'package:app/main.dart' ('lib/main.dart').
Try correcting the name to the name of an existing method, or defining a method named 'setState'.
        onPressed: () => setState(() {}),
                         ^^^^^^^^

"O método setState não está definido para o tipo ProdutoTile." O setState é um método da classe State; um StatelessWidget não tem. E mesmo que tivesse, redesenhar o filho não mudaria o total, que mora no pai. Como consertar: o filho não muda estado nenhum; ele chama a função que recebeu (onPressed: onComprar), e quem roda o setState é o pai.

Copiou o estado do pai para o filho

Um erro sem mensagem: o filho recebe quantidade do pai e, no initState, copia para um _quantidade próprio. Na primeira vez funciona; quando o pai muda o valor, o filho continua mostrando a cópia antiga, porque o initState não roda de novo (veja Ciclo de Vida). Como consertar: não duplique o estado: o filho mostra widget.quantidade direto, e só o pai guarda o valor.

Resumo

  • Dados descem pelo construtor (campos final); avisos sobem por funções (VoidCallback, ValueChanged<T>).
  • Estado guardado num filho fica preso lá: nem o pai nem os irmãos conseguem ler.
  • Elevar o estado: guarde-o no pai mais próximo de todos os que precisam dele; os filhos viram StatelessWidget que recebem valores e funções.
  • Só quem guarda o estado chama setState. Num StatelessWidget, setState nem existe.
  • Não duplique o estado no filho: mostre o valor que veio do pai.
