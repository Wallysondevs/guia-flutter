Flutter InheritedWidget

Na aula Por que Gerenciar o Estado, o carrinho da lojinha precisou "descer" pela árvore de widgets, passando de construtor em construtor, até chegar ao botão que o usava. O Flutter tem um jeito próprio de evitar isso: o InheritedWidget ("widget herdado"). Ele fica lá em cima, guardando um dado, e qualquer widget abaixo dele pode pedir esse dado direto, sem que ninguém no meio precise repassar. Você já usou isso sem saber: Theme.of(context) e MediaQuery.sizeOf(context) funcionam assim.

Você vai aprender
  • A ideia do InheritedWidget: um dado que os widgets de baixo "herdam".
  • Como escrever um: os campos, o método of(context) e o updateShouldNotify.
  • Como juntá-lo a um StatefulWidget para o dado poder mudar.
  • Um carrinho de compras completo, sem repassar nada pelos construtores.
  • O erro real de pedir o dado num lugar que fica acima do InheritedWidget.
  • Por que, no dia a dia, quase todo mundo usa um pacote em cima dele (o Provider).

Os exemplos rodaram no laboratório do guia (Flutter 3.47), com as fotos tiradas depois dos toques indicados.

A ideia: o quadro de avisos do prédio

No prédio da Ana, o síndico não sobe andar por andar entregando o aviso "a água vai faltar amanhã" (passando de mão em mão, de construtor em construtor). Ele cola o aviso no quadro do térreo. Quem mora no prédio, em qualquer andar, olha o quadro quando precisa. E quem olhou fica avisado quando o síndico troca o aviso.

O InheritedWidget é o quadro de avisos. Ele fica num ponto da árvore, e todos os widgets abaixo dele (os moradores do prédio) podem lê-lo com of(context). Quem leu passa a depender dele: quando o dado muda, o Flutter reconstrói só esses widgets. Quem está fora do prédio (acima ou ao lado na árvore) não enxerga o quadro.

1. O carrinho com InheritedWidget

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

const produtos = ['Bolo de cenoura', 'Pão de queijo', 'Brigadeiro'];

// 1. O "quadro de avisos": guarda o dado e o entrega a quem estiver abaixo.
class CarrinhoScope extends InheritedWidget {
  const CarrinhoScope({
    super.key,
    required this.quantidade,
    required this.adicionar,
    required super.child,
  });

  final int quantidade;
  final VoidCallback adicionar;

  static CarrinhoScope of(BuildContext context) {
    final scope = context.dependOnInheritedWidgetOfExactType<CarrinhoScope>();
    if (scope == null) {
      throw FlutterError('Nenhum CarrinhoScope acima deste widget.');
    }
    return scope;
  }

  @override
  bool updateShouldNotify(CarrinhoScope oldWidget) {
    return quantidade != oldWidget.quantidade;
  }
}

// 2. Quem guarda o estado de verdade (e chama setState).
class Carrinho extends StatefulWidget {
  const Carrinho({super.key, required this.child});

  final Widget child;

  @override
  State<Carrinho> createState() => _CarrinhoState();
}

class _CarrinhoState extends State<Carrinho> {
  int _quantidade = 0;

  @override
  Widget build(BuildContext context) {
    return CarrinhoScope(
      quantidade: _quantidade,
      adicionar: () => setState(() => _quantidade++),
      child: widget.child,
    );
  }
}

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const Carrinho(
      child: MaterialApp(
        debugShowCheckedModeBanner: false,
        home: TelaLoja(),
      ),
    );
  }
}

class TelaLoja extends StatelessWidget {
  const TelaLoja({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const TituloCarrinho()),
      body: ListView(
        children: [
          for (final nome in produtos) CartaoProduto(nome: nome),
        ],
      ),
    );
  }
}

// 3. Lá embaixo, quem precisa pede direto ao quadro de avisos.
class TituloCarrinho extends StatelessWidget {
  const TituloCarrinho({super.key});

  @override
  Widget build(BuildContext context) {
    final quantidade = CarrinhoScope.of(context).quantidade;
    return Text('Lojinha · Carrinho: $quantidade');
  }
}

class CartaoProduto extends StatelessWidget {
  const CartaoProduto({super.key, required this.nome});

  final String nome;

  @override
  Widget build(BuildContext context) {
    return ListTile(
      leading: const Icon(Icons.cake),
      title: Text(nome),
      trailing: IconButton(
        tooltip: 'Adicionar $nome',
        icon: const Icon(Icons.add_shopping_cart),
        onPressed: CarrinhoScope.of(context).adicionar,
      ),
    );
  }
}

O código tem três partes, marcadas com 1, 2 e 3 nos comentários.

Parte 1: o quadro de avisos (CarrinhoScope)

class CarrinhoScope extends InheritedWidget
O nosso InheritedWidget. O sufixo Scope ("alcance") é um costume da comunidade para esses widgets.
final int quantidade; final VoidCallback adicionar;
O que ele entrega: o número de itens e uma função para somar um. Campos final: um InheritedWidget não muda; quando o dado muda, um novo CarrinhoScope é criado no lugar dele.
required super.child
O filho: a parte da árvore que vai poder ler o carrinho (aqui, o app inteiro).
static CarrinhoScope of(BuildContext context)
O jeito de ler, por convenção chamado of (como Theme.of). Quem chama escreve CarrinhoScope.of(context).quantidade.
context.dependOnInheritedWidgetOfExactType<CarrinhoScope>()
O coração do mecanismo: "suba pela árvore a partir de mim, ache o CarrinhoScope mais próximo e me registre como dependente dele". Devolve null se não achar nenhum.
if (scope == null) { throw FlutterError('Nenhum CarrinhoScope acima deste widget.'); }
Se ninguém achou o carrinho, em vez de deixar um null seguir adiante (e quebrar num lugar estranho), o of lança um erro com uma mensagem que diz o porquê (veja Quando dá errado). O FlutterError é a classe de erro que o próprio Flutter usa nas mensagens dele. Muitos códigos usam um assert no lugar, que só roda no modo debug.
bool updateShouldNotify(CarrinhoScope oldWidget)
Quando um CarrinhoScope novo substitui o velho, o Flutter pergunta: "devo avisar os dependentes?". Aqui: só se a quantidade mudou.

Parte 2: quem guarda o estado (Carrinho)

O InheritedWidget só entrega; ele não guarda nada que mude. Quem guarda é um StatefulWidget comum, o Carrinho, que tem o _quantidade e chama setState. A cada setState, o build dele cria um CarrinhoScope novo com o número novo; o Flutter compara com o velho (updateShouldNotify) e reconstrói quem leu o carrinho. No MeuApp, o Carrinho envolve o MaterialApp: assim, todas as telas ficam "dentro do prédio".

Parte 3: quem lê (TituloCarrinho e CartaoProduto)

Repare na TelaLoja: ela não recebe nem repassa nada. O TituloCarrinho (na barra) e o CartaoProduto (na lista) pedem direto ao quadro: CarrinhoScope.of(context).quantidade e CarrinhoScope.of(context).adicionar. Acabou o "cano" da aula anterior.

Carrinho                       ← guarda _quantidade (setState)
└── CarrinhoScope              ← o quadro de avisos
    └── MaterialApp
        └── TelaLoja           ← não sabe de carrinho nenhum
            ├── AppBar
            │   └── TituloCarrinho   ← CarrinhoScope.of(context).quantidade
            └── ListView
                └── CartaoProduto (×3) ← CarrinhoScope.of(context).adicionar

Missão: o cartão também quer mostrar o total do carrinho. No CartaoProduto, logo abaixo do title, acrescente subtitle: Text('No carrinho: ${CarrinhoScope.of(context).quantidade}'),. Nenhum construtor muda: o cartão pede direto ao quadro.

2. Você já usa InheritedWidgets

Vários X.of(context) do Flutter são InheritedWidgets que o MaterialApp (e o próprio runApp) põem lá em cima da árvore:

Você escreveO que vem de cima
Theme.of(context)O tema (cores, fontes) do MaterialApp (aula Temas)
MediaQuery.sizeOf(context)O tamanho da tela e outras informações do aparelho (aula Telas de Vários Tamanhos)
Navigator.of(context)O navegador de telas (aula Navigator)
ScaffoldMessenger.of(context)Quem mostra as SnackBars (aula Diálogos e SnackBar)

É por isso que trocar o tema do MaterialApp muda as cores do app inteiro: todo widget que leu o Theme.of(context) depende dele e é reconstruído. (O Navigator e o ScaffoldMessenger usam o mesmo "subir pela árvore" para achar o widget, mesmo que não sejam exatamente um InheritedWidget por dentro.)

3. Outras formas de fazer

InheritedNotifier: o quadro que avisa sozinho

Se o estado já está num ValueNotifier (ou ChangeNotifier), o Flutter tem um InheritedWidget pronto que avisa os dependentes quando ele muda, sem updateShouldNotify nem StatefulWidget por fora (conferido no laboratório: dois toques num botão com CarrinhoScope.of(context).value++ deixaram a barra em Carrinho: 2):

class CarrinhoScope extends InheritedNotifier<ValueNotifier<int>> {
  const CarrinhoScope({super.key, required super.notifier, required super.child});

  static ValueNotifier<int> of(BuildContext context) {
    return context.dependOnInheritedWidgetOfExactType<CarrinhoScope>()!.notifier!;
  }
}
// uso: CarrinhoScope.of(context).value++

Provider: o mesmo, com menos código

Escrever of, updateShouldNotify e o StatefulWidget para cada dado cansa. O pacote Provider é, por dentro, um InheritedWidget com tudo isso pronto: você escreve ChangeNotifierProvider(create: …) lá em cima e context.watch<Carrinho>() lá embaixo. É a próxima aula, Provider.

Entender como o Flutter entrega dados (e ler o código do Provider, do tema…)InheritedWidget escrito à mão, como nesta aula
Um dado simples, sem pacoteInheritedNotifier com um ValueNotifier

"Durante a construção do MeuApp, aconteceu: Nenhum CarrinhoScope acima deste widget." É a mensagem do nosso throw FlutterError(…) (o Flutter chama de assertion os erros do tipo FlutterError). A pilha mostra o caminho: o build do MeuApp (linha 61) chamou o of (linha 22), que lançou o erro. O motivo: o context do MeuApp é o lugar dele na árvore, e o Carrinho (com o CarrinhoScope) é criado dentro do build dele, ou seja, abaixo. O dependOnInheritedWidgetOfExactType só procura para cima, e lá não há nenhum. Sem o nosso if, o null seguiria adiante e o erro seria um Null check operator used on a null value, bem menos claro. Como consertar: leia o carrinho só em widgets que ficam abaixo do Carrinho (como o TituloCarrinho).

Esqueceu de comparar no updateShouldNotify

Se o updateShouldNotify devolver sempre false, o carrinho muda, mas ninguém é avisado: a barra continua com o número velho. Se devolver sempre true, funciona, mas todo dependente é reconstruído a cada setState, mesmo sem mudança. Como fazer: compare os campos que importam: return quantidade != oldWidget.quantidade;.

Leu o dado no initState

No laboratório, o TituloCarrinho virou um StatefulWidget que guardava a quantidade inicial lendo CarrinhoScope.of(context) no initState. O console:

The following assertion was thrown building DefaultTextStyle(…):
dependOnInheritedWidgetOfExactType<CarrinhoScope>() or dependOnInheritedElement() was called before
_TituloCarrinhoState.initState() completed.
When an inherited widget changes, for example if the value of Theme.of() changes, its dependent
widgets are rebuilt. If the dependent widget's reference to the inherited widget is in a constructor
or an initState() method, then the rebuilt dependent widget will not reflect the changes in the
inherited widget.
Typically references to inherited widgets should occur in widget build() methods. Alternatively,
initialization based on inherited widgets can be placed in the didChangeDependencies method, which
is called after initState and whenever the dependencies change thereafter.
…

A própria mensagem explica: "o dependOnInheritedWidgetOfExactType<CarrinhoScope>() foi chamado antes de o initState() terminar. Quando um InheritedWidget muda, os dependentes são reconstruídos; se a leitura está no construtor ou no initState, o widget não vai refletir a mudança. Leia nos métodos build(), ou ponha a preparação no didChangeDependencies, que roda depois do initState e de novo sempre que as dependências mudam". Como fazer: leia no build (ou no didChangeDependencies, veja Ciclo de Vida).

Resumo

  • Um InheritedWidget guarda dados lá em cima da árvore; qualquer widget abaixo lê com X.of(context), sem passar por construtores.
  • O of usa context.dependOnInheritedWidgetOfExactType<X>(), que acha o mais próximo acima e registra a dependência.
  • Para o dado mudar, um StatefulWidget por cima guarda o estado e, a cada setState, cria um InheritedWidget novo; o updateShouldNotify decide quem é reconstruído.
  • Só quem está abaixo enxerga. Chamado acima, o of não acha nada.
  • Theme.of e MediaQuery.sizeOf funcionam assim; o Provider é um InheritedWidget com o trabalho pronto.
