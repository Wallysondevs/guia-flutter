Flutter Organizando um App Maior

Enquanto o app de compras da Ana tinha uma tela, tudo cabia num main.dart. Agora ela quer marcar itens como comprados, guardar a lista no celular, ter uma tela de receitas… Se tudo continuar num arquivo só, ele vira um "macarrão" de 2000 linhas em que mexer num lugar quebra outro. Esta aula mostra como dividir o app em peças com uma função cada, seguindo o guia de arquitetura oficial do Flutter.

Você vai aprender
  • Por que separar: o princípio da separação de responsabilidades.
  • As camadas que a documentação recomenda: UI (View e ViewModel) e dados (Repository e Service).
  • Uma organização de pastas para o lib/.
  • O ViewModel com ChangeNotifier e a tela que o escuta com ListenableBuilder.
  • Como testar a lógica sem tela.
  • import relativo e import 'package:…'.

O projeto desta aula foi montado e testado no Flutter 3.47.7 (Dart 3.13.5) da máquina da Ana; as saídas de terminal e a foto vieram de lá. As ideias de arquitetura resumem o guia oficial docs.flutter.dev/app-architecture, que se baseia no padrão MVVM e avisa: são "diretrizes, não regras fixas".

A ideia: o restaurante

Num restaurante, o garçom anota o pedido e leva o prato, mas não cozinha. O cozinheiro prepara a comida, mas não vai à mesa. A despensa guarda os ingredientes; o fornecedor os entrega. Cada um tem um trabalho, e dá para trocar o fornecedor sem que o cliente perceba. Num app:

No restauranteNo appFazNão faz
Salão e garçomView (os widgets da tela)Mostra os dados e repassa os toquesRegras de negócio, acesso a dados
CozinheiroViewModelTransforma os dados no que a tela mostra; tem os comandos (adicionar, alternar)Desenhar widgets
DespensaRepository (repositório)É a "fonte da verdade" dos dados: guarda, busca, trata errosSaber como a tela é
FornecedorService (serviço)Conversa com o mundo de fora: internet, arquivo, bancoGuardar estado

Duas regras da documentação, que valem decorar:

  • As dependências apontam para baixo: a View conhece o ViewModel, o ViewModel conhece o Repository, o Repository conhece o Service. Nunca o contrário.
  • Os dados sobem, os eventos descem: os dados vão do Repository até a tela; os toques do usuário vão da tela para o ViewModel.
  ┌───────────── camada de UI ─────────────┐
  │  View (TelaCompras)  ⇄  ViewModel       │   toque → comando; dados → redesenho
  └────────────────────────────┬────────────┘
  ┌───────────── camada de dados ┴──────────┐
  │  Repository (ComprasRepository)          │   a fonte da verdade
  │      ↓                                   │
  │  Service (internet, arquivo, banco)      │   o mundo de fora
  └──────────────────────────────────────────┘

2. As peças, uma por arquivo

O modelo

class Item {
  const Item({required this.nome, this.comprado = false});

  final String nome;
  final bool comprado;

  Item copyWith({bool? comprado}) =>
      Item(nome: nome, comprado: comprado ?? this.comprado);
}
final String nome; final bool comprado;
Campos final: um Item não muda depois de criado (é imutável).
copyWith({bool? comprado})
Para "mudar", cria-se uma cópia com o campo trocado. Imutabilidade evita que uma parte do app altere um item escondido de outra.

O repositório

import '../../domain/models/item.dart';

/// Guarda a lista de compras. Hoje, na memória;
/// amanhã, num banco de dados, sem a tela perceber.
class ComprasRepository {
  final List<Item> _itens = [];

  List<Item> buscarTodos() => List.unmodifiable(_itens);

  void adicionar(Item item) => _itens.add(item);

  void substituir(int posicao, Item item) => _itens[posicao] = item;
}
final List<Item> _itens
A lista mora aqui, privada. Hoje na memória; quando a Ana quiser salvar no celular (veja SharedPreferences e SQLite), só este arquivo muda.
List.unmodifiable(_itens)
Entrega uma cópia que não pode ser alterada: ninguém de fora adiciona itens "por trás" do repositório.
import '../../domain/models/item.dart';
Um import relativo: o caminho a partir deste arquivo (.. = a pasta de cima).

O ViewModel

import 'package:flutter/foundation.dart';

import '../../../data/repositories/compras_repository.dart';
import '../../../domain/models/item.dart';

class ComprasViewModel extends ChangeNotifier {
  ComprasViewModel({required this._repositorio});

  final ComprasRepository _repositorio;

  List<Item> get itens => _repositorio.buscarTodos();

  int get faltam => itens.where((item) => !item.comprado).length;

  void adicionar(String nome) {
    final limpo = nome.trim();
    if (limpo.isEmpty) return;
    _repositorio.adicionar(Item(nome: limpo));
    notifyListeners();
  }

  void alternar(int posicao) {
    final item = itens[posicao];
    _repositorio.substituir(posicao, item.copyWith(comprado: !item.comprado));
    notifyListeners();
  }
}
extends ChangeNotifier
Uma classe do Flutter que sabe avisar "mudei!" a quem estiver ouvindo.
ComprasViewModel({required this._repositorio});
Recebe o repositório pronto, de fora (isso se chama injeção de dependência): no teste, dá para passar outro. No Dart 3.13 do lab, um parâmetro nomeado pode iniciar um campo privado direto (this._repositorio), e quem chama escreve sem o sublinhado: ComprasViewModel(repositorio: …). Em versões mais antigas do Dart isso não compila; a forma clássica, que funciona em todas, é ComprasViewModel({required ComprasRepository repositorio}) : _repositorio = repositorio; (é a que o "Experimente" abaixo usa).
get itens / get faltam
O que a tela precisa, já calculado: a lista e quantos itens faltam comprar.
adicionar / alternar
Os comandos: a tela chama, o ViewModel aplica a regra (ignorar nome em branco), fala com o repositório e…
notifyListeners()
… avisa quem está ouvindo para redesenhar. É o setState do ViewModel.

A View (a tela)

import 'package:flutter/material.dart';

import '../view_models/compras_view_model.dart';

class TelaCompras extends StatefulWidget {
  const TelaCompras({super.key, required this.viewModel});

  final ComprasViewModel viewModel;

  @override
  State<TelaCompras> createState() => _TelaComprasState();
}

class _TelaComprasState extends State<TelaCompras> {
  final _campo = TextEditingController();

  @override
  void dispose() {
    _campo.dispose();
    super.dispose();
  }

  void _enviar(String texto) {
    widget.viewModel.adicionar(texto);
    _campo.clear();
  }

  @override
  Widget build(BuildContext context) {
    final viewModel = widget.viewModel;
    return Scaffold(
      appBar: AppBar(title: const Text('Compras da Ana')),
      body: ListenableBuilder(
        listenable: viewModel,
        builder: (context, _) {
          final itens = viewModel.itens;
          return Column(
            children: [
              Padding(
                padding: const EdgeInsets.all(16),
                child: TextField(
                  controller: _campo,
                  decoration: const InputDecoration(labelText: 'Novo item'),
                  onSubmitted: _enviar,
                ),
              ),
              Text('Faltam ${viewModel.faltam} de ${itens.length}'),
              Expanded(
                child: ListView.builder(
                  itemCount: itens.length,
                  itemBuilder: (context, i) => CheckboxListTile(
                    title: Text(itens[i].nome),
                    value: itens[i].comprado,
                    onChanged: (_) => viewModel.alternar(i),
                  ),
                ),
              ),
            ],
          );
        },
      ),
    );
  }
}
final ComprasViewModel viewModel
A tela recebe o seu ViewModel (um para um: cada tela tem o seu).
_campo (TextEditingController)
A tela ainda é StatefulWidget, mas só por causa do controlador do campo de texto: estado de tela, que não interessa a mais ninguém. Os dados da lista não moram aqui.
ListenableBuilder(listenable: viewModel, builder: …)
Escuta o ViewModel e roda o builder de novo a cada notifyListeners(). Só o que está dentro dele é redesenhado.
onChanged: (_) => viewModel.alternar(i)
O toque vira um comando. A tela não decide nada: só repassa.

O main.dart: montando as peças

import 'package:flutter/material.dart';

import 'data/repositories/compras_repository.dart';
import 'ui/compras/view_models/compras_view_model.dart';
import 'ui/compras/widgets/tela_compras.dart';

void main() {
  final repositorio = ComprasRepository();
  runApp(
    MaterialApp(
      title: 'Compras da Ana',
      home: TelaCompras(
        viewModel: ComprasViewModel(repositorio: repositorio),
      ),
    ),
  );
}

O main cria o repositório, entrega ao ViewModel, entrega o ViewModel à tela. Em apps maiores, essa "montagem" costuma ser feita por um pacote como o Provider.

3. Testando a lógica sem tela

A grande vantagem de tirar a lógica da tela: dá para testá-la com um test comum, sem montar widget nenhum (compare com Testes de Widget):

import 'package:flutter_test/flutter_test.dart';

import 'package:compras/data/repositories/compras_repository.dart';
import 'package:compras/ui/compras/view_models/compras_view_model.dart';

void main() {
  test('adicionar e marcar como comprado', () {
    final vm = ComprasViewModel(repositorio: ComprasRepository());

    vm.adicionar('Arroz');
    vm.adicionar('Feijão');
    expect(vm.faltam, 2);

    vm.alternar(0);
    expect(vm.itens[0].comprado, isTrue);
    expect(vm.faltam, 1);
  });

  test('nome em branco é ignorado', () {
    final vm = ComprasViewModel(repositorio: ComprasRepository());

    vm.adicionar('   ');
    expect(vm.itens, isEmpty);
  });
}

Repare no import 'package:compras/…': nos testes (que ficam fora de lib/) usa-se o import de pacote, com o nome do projeto (name: compras no pubspec.yaml) no lugar de lib/.

4. Experimente: tudo num arquivo, separado por blocos

O editor do guia (que roda o código no DartPad) trabalha com um arquivo só. Então a Ana juntou as cinco peças num main.dart, na mesma ordem das pastas, com um comentário marcando cada bloco. É também um bom jeito de começar um app: escreva separado por classes num arquivo e, quando crescer, mova cada bloco para o seu arquivo.

Missão: a Ana não quer "Arroz" duas vezes na lista. Faça o ViewModel (não a tela!) ignorar um nome que já existe: no adicionar, logo depois do if (limpo.isEmpty) return;, acrescente if (itens.any((item) => item.nome == limpo)) return;. Rode, adicione Arroz, Feijão e Arroz de novo, e marque o Feijão.

5. Quando usar tudo isso

Tamanho do appSugestão
Uma tela, um exercícioUm main.dart com widgets pequenos e setState. Arquitetura demais atrapalha.
Algumas telas, dados simplesSepare em arquivos por tela; tire a lógica para um ViewModel quando a tela começar a ter regras.
App de verdade (internet, banco, várias telas)As camadas completas: Views, ViewModels, Repositories, Services, e um pacote para montar as peças (Provider, Riverpod) ou outro padrão de estado (BLoC).

Quando dá errado

A tela não atualiza depois do comando

Faltou o notifyListeners() no fim do comando, ou a parte da tela que mostra o dado está fora do ListenableBuilder. Como resolver: todo comando que muda dados termina com notifyListeners(), e tudo o que mostra dados do ViewModel fica dentro do builder.

Target of URI doesn't exist no import

O caminho do import está errado (um ../ a mais ou a menos, ou o arquivo mudou de pasta). O flutter analyze e o editor apontam a linha. Como resolver: confira o caminho a partir do arquivo atual, ou use o import de pacote (package:compras/…), que não depende de onde o arquivo está. Os editores (VS Code, Android Studio) atualizam os imports sozinhos quando você move um arquivo por eles.

Lógica escondida na tela

Não dá erro, mas é o problema mais comum: um if de regra de negócio dentro do onPressed. Um dia você cria um segundo botão e esquece de copiar a regra. Como resolver: se a decisão é sobre os dados, ela vai para o ViewModel; na tela, só decisões de aparência (mostrar ou esconder, cor, animação).

Resumo

  • Separação de responsabilidades: cada peça com um trabalho. A View mostra; o ViewModel decide; o Repository guarda; o Service busca fora.
  • Dependências para baixo; dados sobem, eventos descem.
  • ViewModel = ChangeNotifier + comandos + notifyListeners(); a tela escuta com ListenableBuilder.
  • UI por funcionalidade (lib/ui/compras/), dados por tipo (lib/data/repositories/).
  • Lógica fora da tela = testes simples, sem widget.
  • Comece simples; adote as camadas quando o app pedir.
