Flutter FutureBuilder

Quase todo app de verdade mostra dados que não estão prontos quando a tela abre: as receitas vêm de um servidor, o saldo vem do banco, a foto vem da internet. Isso leva tempo, às vezes meio segundo, às vezes dez. Enquanto isso, a tela não pode ficar congelada nem em branco: ela precisa mostrar "carregando…", depois os dados, ou uma mensagem de erro se algo falhou. O FutureBuilder é o widget que faz essa troca de telas para você.

Você vai aprender
  • O que é um Future (um valor que vai chegar depois), em uma revisão rápida do Dart.
  • Como o FutureBuilder redesenha a tela quando o valor chega.
  • Os três estados de toda tela que espera dados: carregando, deu certo e deu erro.
  • O AsyncSnapshot: connectionState, hasData, data, hasError e error.
  • Por que o Future deve ser criado no initState, e não dentro do build.
  • A tela vermelha do snapshot.data! quando o dado ainda não chegou.

Os exemplos desta aula foram rodados no laboratório do guia, com o Flutter 3.47. Para não depender da internet, a busca no servidor é de mentirinha: um Future.delayed que espera 2 segundos e devolve uma lista. Na aula Buscando Dados na Internet, você troca essa mentirinha por uma busca de verdade, e o FutureBuilder continua igual.

A ideia: a senha da padaria

Na padaria, a Ana pede um bolo que ainda está no forno. A atendente não faz a Ana esperar parada no balcão: entrega uma senha e diz "quando ficar pronto, eu chamo". A senha não é o bolo; é a promessa de um bolo. Enquanto espera, a Ana pode olhar a vitrine. Quando o número dela é chamado, chegou uma de duas notícias: "seu bolo está pronto" ou "queimou, desculpe".

No Dart, essa senha se chama Future ("futuro"). Uma função async devolve um Future<List<String>>: "uma lista de textos, no futuro". E o FutureBuilder é o painel da padaria: mostra "aguarde" enquanto a senha não é chamada, e troca para o resultado (ou para o aviso de erro) quando ela é.

Revisão de Dart: async, await e Future

Uma função marcada com async sempre devolve um Future. Dentro dela, await espera um outro Future terminar sem travar o app. Fora de um widget, você usaria final receitas = await buscarReceitas();. Mas o método build de um widget não pode ser async nem esperar nada: ele tem de devolver um widget na hora. É por isso que existe o FutureBuilder. (A revisão completa está no Guia Dart.)

1. O primeiro FutureBuilder

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      debugShowCheckedModeBanner: false,
      home: TelaReceitas(),
    );
  }
}

// Finge que vai buscar as receitas num servidor: demora 2 segundos.
Future<List<String>> buscarReceitas() async {
  await Future.delayed(const Duration(seconds: 2));
  return ['Bolo de cenoura', 'Feijoada', 'Pão de queijo'];
}

class TelaReceitas extends StatefulWidget {
  const TelaReceitas({super.key});

  @override
  State<TelaReceitas> createState() => _TelaReceitasState();
}

class _TelaReceitasState extends State<TelaReceitas> {
  late final Future<List<String>> _receitas;

  @override
  void initState() {
    super.initState();
    _receitas = buscarReceitas();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Receitas da Ana')),
      body: FutureBuilder<List<String>>(
        future: _receitas,
        builder: (context, snapshot) {
          if (snapshot.connectionState == ConnectionState.waiting) {
            return const Center(child: CircularProgressIndicator());
          }
          if (snapshot.hasError) {
            return Center(child: Text('Erro: ${snapshot.error}'));
          }
          final receitas = snapshot.data!;
          return ListView(
            children: [
              for (final nome in receitas)
                ListTile(
                  leading: const Icon(Icons.restaurant_menu),
                  title: Text(nome),
                ),
            ],
          );
        },
      ),
    );
  }
}
Future<List<String>> buscarReceitas() async
A "busca no servidor" de mentirinha. O await Future.delayed(…) espera 2 segundos; depois, o return entrega a lista. Quem chama recebe o Future na hora (a senha) e a lista 2 segundos depois.
StatefulWidget e late final Future… _receitas
A tela guarda a senha num campo do State. O late diz ao Dart "vou dar valor a ele antes de usar" (no initState); o final, que ele não muda depois.
initState() { … _receitas = buscarReceitas(); }
A busca começa uma vez, quando a tela nasce (veja Ciclo de Vida). Isso é importante: a seção Quando dá errado mostra o que acontece se você chamar buscarReceitas() dentro do build.
FutureBuilder<List<String>>
O widget que acompanha o Future. O tipo entre < > é o tipo do dado que vai chegar.
future: _receitas
A senha que ele acompanha.
builder: (context, snapshot) { … }
A função que desenha a tela. O FutureBuilder chama ela várias vezes: uma logo de cara (ainda esperando) e outra quando o Future termina. O snapshot ("fotografia instantânea") diz como está o Future naquele momento.
snapshot.connectionState == ConnectionState.waiting
Ainda esperando: mostra a rodinha girando (CircularProgressIndicator) no meio da tela.
snapshot.hasError e snapshot.error
O Future terminou com erro: error guarda o erro que foi lançado.
snapshot.data!
O dado que chegou. Ele é List<String>? (pode ser nulo, porque antes de chegar não existe); o ! diz ao Dart "aqui ele já existe", o que é verdade, porque os dois if acima já trataram a espera e o erro.

2. Quando a busca dá erro

Servidor fora do ar, internet caindo, senha errada: a busca pode falhar. Uma função async que lança uma exceção (com throw) termina o Future com erro, e o FutureBuilder mostra isso em snapshot.hasError. Para ver acontecer, troque o return por um throw:

Future<List<String>> buscarReceitas() async {
  await Future.delayed(const Duration(seconds: 2));
  throw Exception('Sem conexão com o servidor');
}

A tela mostra Erro: Exception: Sem conexão com o servidor. O Erro: veio do nosso Text; o resto é o snapshot.error transformado em texto: Exception: e a mensagem que passamos ao throw. O app não quebrou: o erro foi "pego" pelo FutureBuilder e virou uma tela. É exatamente isso que você quer quando a internet cai.

Missão: a mensagem Exception: … assusta quem usa o app. Troque o texto do erro por 'Não deu para carregar as receitas.'.

3. Outras formas de escrever o builder

Perguntando por hasData primeiro

Em vez de testar a espera, dá para testar o que chegou. É a forma que você mais vai ver em exemplos da internet:

if (snapshot.hasData) {
  return ListaReceitas(receitas: snapshot.data!);
} else if (snapshot.hasError) {
  return Center(child: Text('Erro: ${snapshot.error}'));
}
return const Center(child: CircularProgressIndicator());

Os dois jeitos funcionam. A diferença aparece quando o Future devolve null de propósito (por exemplo, "nenhum usuário logado"): aí hasData é false mesmo com o Future terminado, e a rodinha ficaria girando para sempre. Testar o connectionState primeiro não tem esse problema.

Com switch e padrões do Dart 3

return switch (snapshot) {
  AsyncSnapshot(hasError: true) => Center(child: Text('Erro: ${snapshot.error}')),
  AsyncSnapshot(hasData: true, :final data) => ListaReceitas(receitas: data!),
  _ => const Center(child: CircularProgressIndicator()),
};

Mais curto, mas exige conhecer os padrões (patterns) do Dart 3. Use o que você entende melhor.

Com um valor inicial: initialData

Se você já tem algo para mostrar enquanto espera (a lista da última vez, guardada no aparelho), passe em initialData: const ['Bolo de cenoura']. Aí o snapshot.data já começa com esse valor, e hasData é true desde o início.

SituaçãoQual usar
Um dado que chega uma vez (a lista de receitas, o perfil do usuário)FutureBuilder
Dados que continuam chegando (o cronômetro, as mensagens de um chat)StreamBuilder (próxima aula, StreamBuilder)
A busca precisa ser refeita quando o usuário pede (puxar para atualizar)FutureBuilder com o Future trocado dentro de um setState, ou guardar os dados no estado e chamar setState quando chegarem

Linha por linha: EXCEPTION CAUGHT BY WIDGETS LIBRARY é "exceção pega pela biblioteca de widgets"; The following NullError was thrown building FutureBuilder… diz que o erro aconteceu enquanto o FutureBuilder se desenhava; e Null check operator used on a null value é a causa: "o operador de checagem de nulo (o !) foi usado num valor nulo". Como consertar: trate a espera antes de usar o ! (o if (snapshot.connectionState == ConnectionState.waiting) do exemplo 1), ou teste snapshot.hasData.

Criou o Future dentro do build

Este não mostra erro nenhum, e por isso é traiçoeiro. A Ana pôs um botão de curtir na tela e chamou buscarReceitas() direto no future::

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      debugShowCheckedModeBanner: false,
      home: TelaReceitas(),
    );
  }
}

Future<List<String>> buscarReceitas() async {
  print('Buscando receitas no servidor...');
  await Future.delayed(const Duration(seconds: 2));
  return ['Bolo de cenoura', 'Feijoada', 'Pão de queijo'];
}

class TelaReceitas extends StatefulWidget {
  const TelaReceitas({super.key});

  @override
  State<TelaReceitas> createState() => _TelaReceitasState();
}

class _TelaReceitasState extends State<TelaReceitas> {
  int _curtidas = 0;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('Curtidas: $_curtidas')),
      floatingActionButton: FloatingActionButton(
        tooltip: 'Curtir',
        onPressed: () => setState(() => _curtidas++),
        child: const Icon(Icons.favorite),
      ),
      body: FutureBuilder<List<String>>(
        future: buscarReceitas(), // ERRADO: cria um Future novo a cada build
        builder: (context, snapshot) {
          if (snapshot.connectionState == ConnectionState.waiting) {
            return const Center(child: CircularProgressIndicator());
          }
          return ListView(
            children: [
              for (final nome in snapshot.data!) ListTile(title: Text(nome)),
            ],
          );
        },
      ),
    );
  }
}

No laboratório, o app abriu, esperou a lista e, depois, a Ana tocou uma vez no coração:

E o console mostrou a busca duas vezes, uma quando a tela abriu e outra no toque:

Buscando receitas no servidor...
Buscando receitas no servidor...

O que aconteceu: o setState do botão manda o Flutter rodar o build de novo. O build chama buscarReceitas(), que cria um Future novo; o FutureBuilder vê um Future diferente, volta para waiting e espera tudo de novo. Num app de verdade, isso é uma ida ao servidor a cada curtida, a lista piscando, a internet do usuário gasta à toa. Como consertar: crie o Future no initState, guarde num campo e passe o campo para o future:, como no exemplo 1. O build pode rodar quantas vezes quiser: o Future continua o mesmo.

Esqueceu de tratar o erro

Sem o if (snapshot.hasError), quando a busca falha, o snapshot.data continua nulo, e o snapshot.data! derruba a tela com a mesma tela vermelha do primeiro cenário. Toda tela que espera dados precisa dos três estados: carregando, deu certo e deu erro.

Referência rápida

EscritaO que faz

initialData: valorO dado que o snapshot tem antes de o Future terminar
snapshot.connectionStatenone (sem Future), waiting (esperando), done (terminou)
snapshot.hasData / snapshot.dataSe chegou um dado não nulo / o dado (tipo T?)
snapshot.hasError / snapshot.errorSe o Future terminou com erro / o erro

Resumo

  • Um Future é a promessa de um valor que chega depois. O build não pode esperar; o FutureBuilder espera por ele e redesenha a tela quando o valor chega.
  • O builder recebe um snapshot: connectionState (waiting, done), hasData/data e hasError/error.
  • Toda tela que espera dados tem três estados: carregando (a rodinha), deu certo (os dados) e deu erro (uma mensagem).
  • Crie o Future no initState e guarde num campo. Criado no build, ele recomeça a cada reconstrução.
  • Só use snapshot.data! depois de tratar a espera e o erro; antes disso, ele é null e derruba a tela.
