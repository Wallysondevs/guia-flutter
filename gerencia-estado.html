Flutter Gerência de Estado

Com setState você já faz muita coisa: um contador, um formulário, uma lista que cresce. Mas, quando o app passa de uma tela, aparece um problema novo: vários widgets, em lugares diferentes da árvore, precisam do mesmo dado. O carrinho da lojinha da Ana aparece no topo da tela, em cada produto e na tela de pagamento. Onde esse dado deve morar? Como os widgets ficam sabendo quando ele muda? Responder a isso é o que se chama gerência de estado (state management). Esta aula mostra o problema; as próximas mostram as ferramentas.

Você vai aprender
  • O que é "estado" num app, e a diferença entre estado local e estado do app.
  • O que acontece quando o estado fica no lugar errado (o carrinho que a barra de cima não enxerga).
  • A primeira solução: elevar o estado e passar funções para baixo, e o incômodo de repassar por widgets que não usam.
  • Uma ferramenta que já vem no Flutter: ValueNotifier com ValueListenableBuilder.
  • Um mapa das opções (InheritedWidget, Provider, Riverpod, BLoC) e como escolher.

Os exemplos rodaram no laboratório do guia (Flutter 3.47); as fotos foram tiradas depois de tocar nos botões indicados.

A ideia: o quadro de pedidos da lanchonete

Numa lanchonete pequena, o atendente anota o pedido de cabeça e grita para a cozinha: funciona. Quando a lanchonete cresce (caixa, cozinha, balcão de entrega, motoboy), gritar não basta: alguém esquece, alguém ouve errado. A solução é um quadro de pedidos na parede, que todos veem, e uma regra clara de quem pode escrever nele.

No app é igual. O "de cabeça" é o setState dentro de um widget: ótimo para coisas que só aquele widget usa. O "quadro na parede" é o estado guardado num lugar que vários widgets conseguem ler, e que os avisa quando muda.

Dois tipos de estado

A documentação oficial do Flutter (Differentiate between ephemeral state and app state) separa assim:

Estado local (efêmero)Estado do app (compartilhado)
Quem usaUm widget sóVários widgets, às vezes em telas diferentes
ExemplosA aba escolhida, o texto sendo digitado, uma animação, o "mostrar senha"O carrinho, o usuário logado, as preferências, as mensagens não lidas
FerramentaStatefulWidget + setStateElevar o estado, InheritedWidget, Provider, Riverpod, BLoC…

A própria documentação diz que não há uma regra universal: um estado pode começar local e virar do app quando o app cresce.

1. O estado no lugar errado

A Ana fez a lojinha assim: cada cartão de produto guarda a sua quantidade no carrinho, com setState. Parece natural:

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

const produtos = ['Bolo de cenoura', 'Pão de queijo', 'Brigadeiro'];

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      home: Scaffold(
        // A AppBar quer mostrar o total... mas de onde ela tira esse número?
        appBar: AppBar(title: const Text('Lojinha · Carrinho: 0')),
        body: ListView(
          children: [
            for (final nome in produtos) CartaoProduto(nome: nome),
          ],
        ),
      ),
    );
  }
}

// Cada cartão guarda a SUA conta. Ninguém mais fica sabendo.
class CartaoProduto extends StatefulWidget {
  const CartaoProduto({super.key, required this.nome});

  final String nome;

  @override
  State<CartaoProduto> createState() => _CartaoProdutoState();
}

class _CartaoProdutoState extends State<CartaoProduto> {
  int _quantidade = 0;

  @override
  Widget build(BuildContext context) {
    return ListTile(
      leading: const Icon(Icons.cake),
      title: Text(widget.nome),
      subtitle: Text('No carrinho: $_quantidade'),
      trailing: IconButton(
        tooltip: 'Adicionar ${widget.nome}',
        icon: const Icon(Icons.add_shopping_cart),
        onPressed: () => setState(() => _quantidade++),
      ),
    );
  }
}

Nenhum erro, nenhuma tela vermelha, e o app está errado: a barra diz Carrinho: 0 com 3 itens no carrinho. Cada _CartaoProdutoState tem a sua própria conta, e ela fica presa dentro do cartão. A AppBar está em outro galho da árvore e não tem como ler esses números. E se a Ana tivesse uma tela de pagamento, ela também não saberia. O estado do carrinho é um estado do app, mas foi guardado como estado local.

2. Elevar o estado e passar para baixo

A solução clássica (que você viu em Passando Dados e Elevando o Estado): o estado sobe para o ancestral comum de quem precisa dele, o widget que está acima da barra e dos cartões. Ele guarda o número e passa para baixo uma função para somar:

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

const produtos = ['Bolo de cenoura', 'Pão de queijo', 'Brigadeiro'];

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      debugShowCheckedModeBanner: false,
      home: TelaLoja(),
    );
  }
}

// O estado mora aqui em cima, porque a AppBar e os cartões precisam dele.
class TelaLoja extends StatefulWidget {
  const TelaLoja({super.key});

  @override
  State<TelaLoja> createState() => _TelaLojaState();
}

class _TelaLojaState extends State<TelaLoja> {
  int _noCarrinho = 0;

  void _adicionar() {
    setState(() => _noCarrinho++);
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text('Lojinha · Carrinho: $_noCarrinho')),
      body: ListaProdutos(onAdicionar: _adicionar),
    );
  }
}

// A lista não usa o onAdicionar: só repassa para os cartões.
class ListaProdutos extends StatelessWidget {
  const ListaProdutos({super.key, required this.onAdicionar});

  final VoidCallback onAdicionar;

  @override
  Widget build(BuildContext context) {
    return ListView(
      children: [
        for (final nome in produtos)
          CartaoProduto(nome: nome, onAdicionar: onAdicionar),
      ],
    );
  }
}

class CartaoProduto extends StatelessWidget {
  const CartaoProduto({super.key, required this.nome, required this.onAdicionar});

  final String nome;
  final VoidCallback onAdicionar;

  @override
  Widget build(BuildContext context) {
    return ListTile(
      leading: const Icon(Icons.cake),
      title: Text(nome),
      trailing: IconButton(
        tooltip: 'Adicionar $nome',
        icon: const Icon(Icons.add_shopping_cart),
        onPressed: onAdicionar,
      ),
    );
  }
}
_TelaLojaState com int _noCarrinho
O estado mora na tela, que contém a AppBar e a lista. Os dois "enxergam" o mesmo número.
void _adicionar() { setState(…) }
Só quem guarda o estado o muda. Os outros recebem a função.
ListaProdutos({required this.onAdicionar})
A lista recebe a função… e só a repassa. Ela mesma não usa.
CartaoProduto(… onAdicionar)
Lá embaixo, o botão chama a função que veio "descendo" pela árvore.

Funciona. Mas olhe o caminho que o dado faz:

TelaLoja            ← guarda _noCarrinho e _adicionar
├── AppBar          ← usa _noCarrinho
└── ListaProdutos   ← NÃO usa, só repassa onAdicionar
    └── CartaoProduto (×3)  ← usa onAdicionar

A ListaProdutos virou um "cano" por onde a função só passa. Aqui é um nível; num app real, entre a tela e o botão há cinco, seis widgets, e cada um precisa de um parâmetro novo a cada dado novo (o nome do usuário, o tema, o carrinho…). Esse incômodo tem até nome em inglês: prop drilling ("furar" os widgets para passar um dado). E, a cada setState na TelaLoja, a tela inteira é reconstruída, mesmo que só a barra precise mudar.

3. Uma ferramenta que já vem no Flutter: ValueNotifier

O Flutter traz uma caixinha que guarda um valor e avisa quem estiver ouvindo quando ele muda: o ValueNotifier. E um widget que ouve essa caixinha e se redesenha sozinho: o ValueListenableBuilder.

import 'package:flutter/material.dart';

// O estado do carrinho fica fora dos widgets, num ValueNotifier.
final carrinho = ValueNotifier<int>(0);

void main() => runApp(const MeuApp());

const produtos = ['Bolo de cenoura', 'Pão de queijo', 'Brigadeiro'];

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      home: Scaffold(
        appBar: AppBar(
          // Só este pedaço é redesenhado quando o carrinho muda.
          title: ValueListenableBuilder<int>(
            valueListenable: carrinho,
            builder: (context, quantidade, child) {
              return Text('Lojinha · Carrinho: $quantidade');
            },
          ),
        ),
        body: ListView(
          children: [
            for (final nome in produtos) CartaoProduto(nome: nome),
          ],
        ),
      ),
    );
  }
}

class CartaoProduto extends StatelessWidget {
  const CartaoProduto({super.key, required this.nome});

  final String nome;

  @override
  Widget build(BuildContext context) {
    return ListTile(
      leading: const Icon(Icons.cake),
      title: Text(nome),
      trailing: IconButton(
        tooltip: 'Adicionar $nome',
        icon: const Icon(Icons.add_shopping_cart),
        onPressed: () => carrinho.value++,
      ),
    );
  }
}
final carrinho = ValueNotifier<int>(0);
A caixinha, com o valor inicial 0. Aqui ela está fora de qualquer widget (uma variável do arquivo), para ficar simples.
carrinho.value++
Mudar o value já avisa os ouvintes. Não há setState: o cartão nem precisa ser StatefulWidget.
ValueListenableBuilder<int>(valueListenable: carrinho, builder: …)
Ouve a caixinha e roda o builder a cada mudança, com o valor novo (quantidade). Só esse pedaço (o título da barra) é redesenhado.
Uma variável global resolve tudo?

Para um exemplo, sim. Num app de verdade, uma variável solta no arquivo é difícil de testar (todos os testes dividem o mesmo carrinho) e qualquer parte do código pode mexer nela. Por isso as ferramentas das próximas aulas entregam o estado pela árvore de widgets: quem está abaixo pede, e o Flutter acha.

Missão: ponha um botão para esvaziar o carrinho: na AppBar, acrescente actions: [IconButton(tooltip: 'Esvaziar', icon: const Icon(Icons.remove_shopping_cart), onPressed: () => carrinho.value = 0)]. Toque em adicionar algumas vezes e depois esvazie.

4. O mapa das opções

Existem dezenas de pacotes de gerência de estado. A documentação oficial lista várias (List of state management approaches). Este guia mostra as mais usadas, uma por aula:

FerramentaEm uma fraseAula
setStateEstado dentro de um widget sósetState
Elevar o estadoO estado sobe para o ancestral comum; dados e funções descem pelos construtoresElevando o Estado
ValueNotifier / ChangeNotifierUma caixinha que avisa quando muda (já vem no Flutter)Esta aula
InheritedWidgetO mecanismo do próprio Flutter para entregar dados a qualquer widget abaixo (é o que o Theme.of(context) usa)InheritedWidget
ProviderUm pacote que deixa o InheritedWidget fácil de usar; é o que a documentação oficial usa no tutorial de estado simplesProvider
RiverpodDo mesmo autor do Provider, sem depender do context, com mais checagens do compiladorRiverpod
BLoCEventos entram, estados saem (com Streams); muito usado em equipes grandesUma Olhada no BLoC
Qual escolher?

Comece pelo mais simples que resolve. Estado de um widget só: setState. Dois ou três widgets próximos: eleve o estado. Um dado que muitas telas usam: Provider (ou Riverpod). Não existe a "melhor" para todo app; existe a que a sua equipe entende e usa do mesmo jeito em todo o código.

Quando dá errado

O estado ficou dentro do widget errado

É o exemplo da seção 1: nenhuma mensagem de erro, mas a tela mostra números que não batem (a barra diz 0, os cartões dizem 1 e 2). Sempre que dois widgets precisam do mesmo dado, pergunte: quem é o ancestral comum dos dois? O estado mora ali (ou acima).

Mudou o valor, mas a tela não mudou

Com ValueNotifier, quem não está dentro de um ValueListenableBuilder não é avisado. Se a Ana escrever Text('Carrinho: ${carrinho.value}') direto na AppBar, o texto mostra o valor da hora em que foi construído e fica parado. O mesmo vale para um campo comum mudado sem setState: o valor muda na memória, mas ninguém mandou redesenhar. Como consertar: leia o valor dentro do builder que ouve a mudança (ou mude dentro do setState).

Uma lista dentro do ValueNotifier

Com ValueNotifier<List<String>>, fazer itens.value.add('Bolo') não avisa ninguém: o ValueNotifier só avisa quando o value é trocado por outro objeto, e a lista é a mesma. Como consertar: troque por uma lista nova: itens.value = [...itens.value, 'Bolo'];.

Referência rápida

EscritaO que faz
setState(() { … })Muda o estado local e redesenha aquele widget
final VoidCallback onAdicionar;Recebe uma função de cima (elevar o estado)
ValueNotifier<T>(inicial)Guarda um valor e avisa quando .value é trocado
ValueListenableBuilder<T>(valueListenable: n, builder: (context, valor, child) => …)Redesenha um pedaço da tela quando o ValueNotifier muda

Resumo

  • Estado local (de um widget só) fica com setState. Estado do app (usado por vários widgets) precisa morar num lugar que todos alcancem.
  • Estado no widget errado não dá erro: dá números que não batem.
  • Elevar o estado resolve, mas obriga widgets do meio a repassar dados e funções que não usam (prop drilling).
  • ValueNotifier + ValueListenableBuilder avisam e redesenham só o pedaço que precisa, sem pacote nenhum.
  • Para entregar estado pela árvore, o Flutter tem o InheritedWidget, a base do Provider e de outras ferramentas: é a próxima aula.
