Flutter iOS, Web e Desktop

A grande promessa do Flutter é escrever o app uma vez e rodar em vários lugares: Android, iPhone, navegador, Windows, Mac e Linux. O código do lib/ é o mesmo; o que muda é o empacotamento no fim, feito com flutter build + o nome da plataforma. Na aula Gerando o APK você viu o Android. Aqui vêm as outras cinco, e a regra mais importante delas: cada uma tem de ser gerada na máquina certa.

Você vai aprender
  • Qual computador gera qual plataforma (e por que o iPhone exige um Mac).
  • Como gerar o app para a web com flutter build web, o que vai na pasta build/web e como testar.
  • O que é o modo Wasm na web.
  • Como gerar o app de desktop (flutter build linux, windows, macos).
  • Os passos do iOS: Xcode, assinatura e flutter build ipa.
  • As mensagens reais quando o computador não serve para aquela plataforma.

A Ana usa um notebook com Linux e Flutter 3.47.7. As saídas desta página vieram dele; o que depende de Mac ou Windows está marcado como ilustrativo, com base na documentação oficial (docs.flutter.dev/deployment).

A ideia: a mesma receita, fornos diferentes

A Ana tem uma receita de pão de queijo. A massa é sempre a mesma (o seu código Dart). Mas para assar, ela precisa do forno certo: forno a gás em casa, forno elétrico na casa da mãe, air fryer no trabalho. Cada forno tem o seu jeito, e você não assa no forno da vizinha sem ir até a casa dela.

No Flutter, os "fornos" são as ferramentas de cada sistema: o Xcode da Apple (que só existe no macOS), o Visual Studio da Microsoft para o Windows, o compilador do Linux. Por isso:

O próprio Flutter avisa isso. No Linux da Ana, a lista de subcomandos do flutter build nem mostra ios, ipa, macos nem windows:

"Subcomandos disponíveis": AAR (biblioteca Android), APK, App Bundle, os arquivos de assets, Linux e web. É a lista do que este computador consegue gerar.

1. Web: flutter build web

A web é a plataforma mais fácil de publicar: qualquer computador gera, e o resultado é uma pasta de arquivos comuns que qualquer servidor de sites entrega. Dentro da pasta do projeto de compras:

$ flutter build web
Compiling lib/main.dart for the Web...
Wasm dry run succeeded. Consider building and testing your application with the `--wasm` flag. See docs for more info: https://docs.flutter.dev/platform-integration/web/wasm
Use --no-wasm-dry-run to disable these warnings.
Font asset "CupertinoIcons.ttf" was tree-shaken, reducing it from 257628 to 1472 bytes (99.4% reduction). Tree-shaking can be disabled by providing the --no-tree-shake-icons flag when building your app.
Font asset "MaterialIcons-Regular.otf" was tree-shaken, reducing it from 1645184 to 7800 bytes (99.5% reduction). Tree-shaking can be disabled by providing the --no-tree-shake-icons flag when building your app.
Compiling lib/main.dart for the Web...                             40.2s
✓ Built build/web
Compiling lib/main.dart for the Web...
O compilador transforma o seu Dart em JavaScript otimizado. Levou 40,2 segundos.
Wasm dry run succeeded…
"O ensaio do Wasm deu certo. Considere gerar e testar o app com a opção --wasm." O Flutter testou, sem gerar nada, se o seu app poderia ser compilado para WebAssembly (veja abaixo), e deu que sim. --no-wasm-dry-run desliga esse aviso.
Font asset … was tree-shaken
As fontes de ícones (Cupertino e Material) foram "sacudidas": só ficaram os ícones que o app usa.
✓ Built build/web
Pronto: o site está na pasta build/web.

Dentro da pasta:

build/web/
├── index.html               « a página que o navegador abre primeiro
├── flutter_bootstrap.js     « o "dá a partida": escolhe e carrega o motor
├── flutter.js
├── main.dart.js             « o SEU app, em JavaScript (2,4 MB)
├── flutter_service_worker.js
├── manifest.json            « nome e ícones, para "instalar" o site como app
├── favicon.png
├── icons/
├── assets/                  « imagens, fontes e outros assets do app
├── canvaskit/               « o motor de desenho, em WebAssembly
└── version.json

A pasta inteira ocupou 40 MB na máquina da Ana; a maior parte é a canvaskit/, que traz versões do motor para navegadores diferentes. O visitante não baixa tudo: só o que o navegador dele usa.

Testando a pasta build/web

Abrir o index.html com dois cliques não funciona: o navegador bloqueia vários arquivos quando a página vem do disco (file://) e a tela fica em branco. A pasta precisa ser servida por um servidor web. Para testar no seu computador, qualquer servidor simples serve, por exemplo o do Python:

$ cd build/web
$ python3 -m http.server 8000

e abra http://localhost:8000. Para publicar de verdade, envie o conteúdo de build/web para um serviço de sites estáticos (GitHub Pages, Firebase Hosting, Netlify…). Se o site não fica na raiz do domínio (por exemplo https://ana.github.io/compras/), gere com --base-href /compras/, senão o app procura os arquivos no lugar errado.

Wasm: o modo mais rápido

Por padrão, o Dart vira JavaScript. Com --wasm, ele vira WebAssembly, um formato que o navegador roda mais perto da velocidade de um app nativo:

$ flutter build web --release --wasm

Segundo a documentação do Flutter 3.47, o app e os pacotes precisam usar o package:web (e não o antigo dart:html), e o navegador do visitante precisa suportar o recurso de coleta de lixo do Wasm (WasmGC). Quando o navegador não suporta, o Flutter carrega a versão JavaScript no lugar.

Rodar na web durante o desenvolvimento

Para desenvolver, você não precisa gerar a pasta toda vez: flutter run -d chrome abre o app no Chrome com hot reload (veja flutter run).

2. Desktop: Linux, Windows e Mac

O app de desktop é uma janela comum do sistema, como qualquer programa. O projeto do flutter create já traz as pastas linux/, windows/ e macos/ com o código nativo de cada uma.

Linux

No notebook da Ana, que é Linux:

$ flutter build linux
Building Linux application...
✓ Built build/linux/x64/release/bundle/compras

Levou 31 segundos. O resultado é uma pasta, não um arquivo só:

build/linux/x64/release/bundle/
├── compras     « o programa (rode com ./compras)
├── data/       « os assets do app e o código Dart compilado
└── lib/        « as bibliotecas do motor do Flutter

A pasta toda tem 24 MB, e é ela inteira que você entrega (num .tar.gz, por exemplo). Para compilar no Linux, o Flutter precisa de alguns pacotes do sistema (compilador C++, CMake, Ninja, GTK 3); o flutter doctor avisa se faltar algum.

Windows (ilustrativo)

Num PC com Windows e o Visual Studio (com a carga de trabalho "Desenvolvimento para desktop com C++"), o comando é flutter build windows, e o programa sai em build\windows\x64\runner\Release\: o .exe junto com DLLs e uma pasta data. Para distribuir, entregue a pasta inteira, não só o .exe. No Linux, a Ana tentou só para ver:

$ flutter build windows
"build windows" only supported on Windows hosts.

"build windows só é suportado em máquinas Windows."

macOS (ilustrativo)

Num Mac com Xcode, flutter build macos gera o .app em build/macos/Build/Products/Release/. A partir do Flutter 3.47, o mínimo é o macOS 12. Para distribuir fora da Mac App Store, a Apple exige que o app seja assinado e "notarizado" (verificado por ela).

3. iOS: o iPhone (ilustrativo)

Para o iPhone não tem atalho: é preciso um Mac com o Xcode. Mesmo com o melhor PC do mundo, um Linux ou Windows não gera o app de iPhone. No Linux da Ana:

$ flutter build ios
Could not find a subcommand named "ios" for "flutter build".

Run 'flutter -h' (or 'flutter <command> -h') for available flutter commands and options.

"Não encontrei um subcomando chamado ios para flutter build." No Linux, o comando simplesmente não existe.

No Mac, os passos, segundo a documentação oficial, são:

  1. Instalar o Xcode (da App Store) e conferir com flutter doctor (veja flutter doctor).
  2. Ter uma conta de desenvolvedor da Apple. Para testar no seu iPhone, a conta gratuita basta; para publicar na App Store, é a paga (anual).
  3. Abrir ios/Runner.xcworkspace no Xcode e escolher a equipe (Team) em Signing & Capabilities: é a assinatura, que prova à Apple quem fez o app.
  4. Testar no aparelho: flutter run com o iPhone ligado no cabo.
  5. Gerar o pacote da loja: flutter build ipa, que cria o .ipa em build/ios/ipa/. O envio para a loja está na aula Publicando nas Lojas.
Novidade do 3.47

O iOS mínimo passou a ser o iOS 15, e o Swift Package Manager vai substituindo o CocoaPods. Veja Novidades do Flutter.

4. Qual plataforma escolher primeiro

  • Android: o mais barato para começar (qualquer computador, taxa única na Play Store). É o foco deste guia.
  • Web: ótimo para mostrar o app para alguém sem instalar nada. Só lembre que a primeira carga é mais pesada que a de um site comum.
  • Desktop: para ferramentas de uso interno, na máquina que você já tem.
  • iOS: só quando tiver acesso a um Mac (seu, emprestado ou alugado na nuvem).

Quando dá errado

Could not find a subcommand named "ios"

Você está num Linux ou num Windows. Não há o que configurar: o iOS (e o macOS) só são gerados num Mac. Use outro computador ou um serviço de compilação na nuvem com Mac.

"build windows" only supported on Windows hosts.

A mesma ideia: só um Windows gera o app de Windows, só um Linux gera o de Linux.

O site abre em branco

Dois motivos comuns: você abriu o index.html com dois cliques (sem servidor), ou o site está numa subpasta e você gerou sem --base-href. Abra o console do navegador (F12): os arquivos que não carregaram aparecem em vermelho. Como resolver: sirva a pasta com um servidor e gere com flutter build web --base-href /nome-da-pasta/.

Um pacote não funciona na web ou no desktop

Nem todo pacote do pub.dev suporta todas as plataformas (um pacote de câmera pode não ter versão para Linux, por exemplo). Na página do pacote, as etiquetas Android, iOS, Web, Linux, macOS, Windows mostram onde ele funciona. Veja Pacotes.

Resumo

  • O código é um só; o empacotamento muda: flutter build + apk, appbundle, web, linux, windows, macos, ipa.
  • Cada sistema gera o seu: iOS e macOS só no Mac (com Xcode), Windows só no Windows, Linux só no Linux. Android e web, em qualquer um.
  • flutter build -h mostra o que o seu computador consegue gerar.
  • A web sai na pasta build/web, que precisa de um servidor; --base-href para subpastas; --wasm para WebAssembly.
  • iOS exige conta Apple e assinatura no Xcode.
