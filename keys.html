Flutter Keys

Desde a primeira aula, todo widget que você escreveu tinha um {super.key} no construtor, e até agora ninguém usou. Esta aula mostra para que ele serve. Uma key ("chave") é um crachá que você pendura num widget para o Flutter saber quem é quem quando a lista muda de ordem. Sem crachá, num caso específico, o estado vai parar no widget errado, e o resultado é um bug estranho, sem mensagem de erro nenhuma.

Você vai aprender
  • Como o Flutter decide qual State pertence a qual widget depois de um build.
  • O bug de trocar a ordem de widgets com estado (fotos reais).
  • Como o ValueKey resolve.
  • Os tipos de chave: ValueKey, ObjectKey, UniqueKey e GlobalKey, e quando usar cada um.
  • A tela vermelha real de Duplicate keys found.

As telas e o console desta aula vieram de um Flutter de verdade, no laboratório da Ana, em tamanho de celular.

A ideia: as cadeiras da sala

Na sala de aula, cada carteira tem um caderno em cima. Se a professora disser "a Ana e a Bia trocam de lugar" e as duas trocarem sem levar o caderno, cada uma vai encontrar o caderno da outra. A carteira foi reconhecida pela posição (1ª, 2ª), e não pela dona.

É assim que o Flutter faz por padrão. Depois de um build, ele compara a lista nova de filhos com a antiga, posição por posição: se na posição 1 havia um CartaoPontos e continua havendo um CartaoPontos, ele reaproveita o State que já estava lá (o caderno da carteira), só trocando os parâmetros. Uma key é a etiqueta com o nome da dona no caderno: com ela, o Flutter procura o State pela etiqueta, e não pela posição.

1. O bug: os pontos ficaram na posição

O placar da Ana e da Bia: cada CartaoPontos guarda os seus pontos (um StatefulWidget), e um botão troca a ordem das jogadoras:

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(home: Placar());
  }
}

class Placar extends StatefulWidget {
  const Placar({super.key});

  @override
  State<Placar> createState() => _PlacarState();
}

class _PlacarState extends State<Placar> {
  List<String> _jogadoras = ['Ana', 'Bia'];

  void _trocar() {
    setState(() {
      _jogadoras = _jogadoras.reversed.toList();
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Placar')),
      body: Column(
        children: [
          for (final nome in _jogadoras) CartaoPontos(nome: nome),
          const SizedBox(height: 16),
          FilledButton(onPressed: _trocar, child: const Text('Trocar a ordem')),
        ],
      ),
    );
  }
}

class CartaoPontos extends StatefulWidget {
  const CartaoPontos({super.key, required this.nome});

  final String nome;

  @override
  State<CartaoPontos> createState() => _CartaoPontosState();
}

class _CartaoPontosState extends State<CartaoPontos> {
  int _pontos = 0;

  @override
  Widget build(BuildContext context) {
    return ListTile(
      title: Text(widget.nome, style: const TextStyle(fontSize: 22)),
      subtitle: Text('$_pontos pontos'),
      trailing: IconButton(
        icon: const Icon(Icons.add_circle),
        tooltip: 'Ponto para ${widget.nome}',
        onPressed: () => setState(() => _pontos++),
      ),
    );
  }
}

A Ana marcou dois pontos (dois toques no ⊕ da Ana) e depois tocou em Trocar a ordem:

Os nomes trocaram de lugar, mas os pontos ficaram onde estavam: agora a Bia tem os 2 pontos da Ana. Nenhuma mensagem no console. O que aconteceu, passo a passo:

  1. Antes: posição 1 = CartaoPontos('Ana') com um State de 2 pontos; posição 2 = CartaoPontos('Bia') com um State de 0.
  2. O setState do placar roda o build de novo, que agora monta CartaoPontos('Bia') na posição 1 e CartaoPontos('Ana') na 2.
  3. O Flutter compara posição por posição: na posição 1, "era um CartaoPontos, continua sendo um CartaoPontos". Ele reaproveita o State da posição 1 (o de 2 pontos) e só troca o parâmetro nome para "Bia".
  4. Resultado: o State de 2 pontos agora mostra "Bia".
Por que nunca tinha dado problema antes?

Porque o bug só aparece quando as três coisas acontecem juntas: widgets com estado (StatefulWidget), do mesmo tipo, lado a lado numa lista que muda (troca de ordem, item apagado no meio, item inserido no começo). Se o estado estivesse no pai (veja Elevando o Estado), os cartões seriam StatelessWidget e não haveria nada para trocar de lugar.

2. A solução: uma ValueKey em cada cartão

Uma linha muda: cada cartão ganha uma chave com o nome da jogadora.

          for (final nome in _jogadoras) CartaoPontos(key: ValueKey(nome), nome: nome),
key:
O parâmetro que todo widget aceita: é o {super.key} do construtor, que passa a chave para a classe Widget.
ValueKey(nome)
Uma chave feita de um valor: o nome da jogadora. Duas ValueKey são iguais quando os valores são iguais (ValueKey('Ana') == ValueKey('Ana')).

Os mesmos toques: dois pontos para a Ana e Trocar a ordem:

Agora o Flutter compara pelas chaves: "o State que era da chave 'Ana' vai para onde está o widget com a chave 'Ana'". Os pontos foram junto com a dona.

Missão: rode o placar sem chave, dê dois pontos para a Ana e toque em "Trocar a ordem": veja os pontos mudarem de dona. Depois conserte: dê a cada CartaoPontos a chave key: ValueKey(nome) e repita.

3. Os tipos de chave: qual usar

ChaveFeita deUse quando
ValueKey(valor)Um valor simples e único: o nome, o id do produtoQuase sempre. Itens de lista que têm um identificador
ObjectKey(objeto)A identidade de um objeto (o mesmo objeto na memória)Os itens são objetos sem um campo único, mas cada um é uma instância diferente
UniqueKey()Nada: cada UniqueKey() é diferente de todas as outrasQuando você quer forçar um State novo (a chave muda a cada build, e o estado recomeça do zero)
GlobalKey()Uma chave única no app inteiroPara alcançar o State de um widget de fora dele. O uso mais comum é o GlobalKey<FormState> do Form
Não use o índice como chave

ValueKey(i), com a posição da lista, é a mesma coisa que não ter chave: depois da troca, a posição 0 continua sendo ValueKey(0), e o estado continua indo para a posição. A chave tem de ser algo que vai junto com o item (o nome, o id), não algo que depende de onde ele está.

Nas listas grandes, o lugar mais comum das chaves é o ListView.builder e o Dismissible (que exige uma chave em cada item).

Quando dá errado

Duas chaves iguais na mesma lista

A lista ficou com a Ana duas vezes (['Ana', 'Ana']), e cada cartão ganhou ValueKey(nome), ou seja, duas vezes ValueKey('Ana'):

Esta é a famosa tela vermelha do Flutter: quando um widget falha ao ser montado (aqui, a Column), o modo debug desenha a mensagem do erro no lugar dele, em amarelo sobre vermelho. O AppBar continuou aparecendo porque não foi ele que falhou. No console, a mesma mensagem, com mais detalhes:

When the exception was thrown, this was the stack:
« … umas 30 linhas com a pilha de chamadas (o caminho dentro do Flutter) …
════════════════════════════════════════════════════════════════════════════════════════════════════

"Chaves duplicadas encontradas. Se vários widgets com chave são filhos de um mesmo widget, as chaves têm de ser únicas." E aponta o culpado: a Column tem mais de um filho com a chave [<'Ana'>] (é assim que uma ValueKey('Ana') aparece escrita). Repare que o relevant error-causing widget aponta o Scaffold da linha 32, e não a Column: nem sempre ele acerta o culpado exato, mas mostra a região do código onde procurar. Como consertar: use na chave algo que seja realmente único para cada item: um id, em vez do nome.

A chave no widget errado

A chave tem de estar no widget que é filho direto da lista que muda (aqui, o CartaoPontos, filho da Column). Se você embrulhar o cartão num Padding e puser a chave no cartão de dentro, o Flutter compara os Padding pela posição, e o bug volta. Como consertar: ponha a chave no widget de fora: Padding(key: ValueKey(nome), …).

Resumo

  • Sem chave, o Flutter reaproveita o State pela posição e pelo tipo do widget.
  • Quando widgets com estado, do mesmo tipo, trocam de ordem, o estado fica na posição e "muda de dono", sem erro nenhum.
  • Uma ValueKey com algo único do item (nome, id) faz o estado ir junto com o item. Nunca use a posição como chave.
  • ObjectKey usa a identidade do objeto; UniqueKey força um estado novo; GlobalKey alcança um State de fora.
  • Chaves iguais entre irmãos dão a tela vermelha Duplicate keys found.
