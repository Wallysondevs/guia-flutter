As Pastas de um Projeto

Na aula Criando um Projeto, o flutter create escreveu 131 arquivos. Parece muito, mas a boa notícia é que, no dia a dia, você mexe em dois: o lib/main.dart (o código do app) e o pubspec.yaml (a ficha do projeto). Esta aula é um passeio pela casa: o que é cada pasta, o que você edita, o que você só olha e o que nunca deve tocar.

Você vai aprender
  • A árvore de pastas de um projeto novo, com as pastas escondidas.
  • A pasta lib, onde mora o seu código.
  • O pubspec.yaml, linha por linha: nome, versão, SDK e pacotes.
  • O pubspec.lock, a pasta test e o analysis_options.yaml.
  • As pastas das plataformas: android, ios, web, linux, macos, windows.
  • O que vai para o Git e o que não vai.
  • O erro real de um pubspec.yaml com um espaço a menos.

Tudo foi conferido na máquina da Ana, no projeto receitas_da_ana recém-criado com o Flutter 3.47.7.

A ideia: a casa e os cômodos

Numa casa, você passa o dia na sala e na cozinha. A caixa de luz e o encanamento estão lá, são importantes, mas você só mexe neles quando precisa, e com cuidado. E tem o quartinho de bagunça, que se arruma sozinho.

2. lib/: onde você trabalha

$ tree lib test
lib
└── main.dart
test
└── widget_test.dart

2 directories, 2 files

No começo, a pasta lib (de library, "biblioteca") tem um arquivo só: o main.dart, com a função main, por onde o app começa. Conforme o app cresce, você cria mais arquivos e subpastas dentro de lib: uma tela por arquivo, por exemplo lib/telas/receita.dart. A organização de um app grande é assunto da aula Organizando um App Maior.

Todo código Dart do app fica em lib/

Um arquivo .dart fora de lib (na raiz do projeto, por exemplo) não entra no app. E não mude o nome do main.dart: o flutter run procura justamente o lib/main.dart.

Missão: este é o lib/main.dart de um projeto criado com flutter create --empty. Troque o 'Hello World!' por 'Lista de compras da Ana'.

import 'package:flutter/material.dart';

void main() {
  runApp(const MainApp());
}

class MainApp extends StatelessWidget {
  const MainApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      home: Scaffold(body: Center(child: Text('Hello World!'))),
    );
  }
}

3. pubspec.yaml: a ficha do projeto

O pubspec.yaml vem cheio de comentários (as linhas que começam com #) explicando cada parte. Sem eles, é isto:

$ grep -v "^ *#" pubspec.yaml | cat -s
name: receitas_da_ana
description: "A new Flutter project."
publish_to: 'none' # Remove this line if you wish to publish to pub.dev

version: 1.0.0+1

environment:
  sdk: ^3.13.5

dependencies:
  flutter:
    sdk: flutter

  cupertino_icons: ^1.0.8

dev_dependencies:
  flutter_test:
    sdk: flutter

  flutter_lints: ^6.0.0

flutter:

  uses-material-design: true

(O grep -v "^ *#" mostra só as linhas que não são comentário, e o cat -s junta as linhas em branco repetidas.)

name: receitas_da_ana
O nome do projeto (o nome do pacote Dart), o mesmo do flutter create. É ele que aparece nos import 'package:receitas_da_ana/...'.
description
Uma frase sobre o projeto. Troque à vontade.
publish_to: 'none'
"Não publicar": impede que o app seja mandado por engano para o pub.dev, o site de pacotes do Dart. O comentário diz: "remova esta linha se quiser publicar no pub.dev" (não é o caso de um app).
version: 1.0.0+1
A versão do app. Antes do +, a versão que o usuário vê (1.0.0); depois, o número de build (1), que precisa aumentar a cada envio para a loja (aula Publicando nas Lojas).
environment: sdk: ^3.13.5
As versões do Dart com que o projeto funciona. O ^ quer dizer "esta ou mais nova, sem mudar o primeiro número": de 3.13.5 até antes da 4.0.0.
dependencies:
Os pacotes que o app usa. O flutter (o próprio framework) e o cupertino_icons (os ícones no estilo iPhone) vêm de fábrica. Os pacotes que você acrescentar (aula Pacotes do pub.dev) entram aqui.
dev_dependencies:
Pacotes usados só durante o desenvolvimento, que não vão dentro do app: o flutter_test (para os testes) e o flutter_lints (as regras de boas práticas que o analisador confere).
flutter: uses-material-design: true
Configurações do Flutter. Esta linha inclui no app a fonte de ícones do Material (os Icons.add, Icons.home...). É também nesta seção que entram as imagens e as fontes do app (aulas Assets (Imagens e Arquivos do App) e Fontes Personalizadas).
YAML: os espaços mandam

O .yaml é um formato de texto em que a indentação (os espaços no começo da linha) diz quem está dentro de quem. O sdk: flutter tem 4 espaços porque está dentro do flutter:, que tem 2 porque está dentro do dependencies:. Um espaço a mais ou a menos muda o sentido, ou quebra o arquivo inteiro (veja em Quando dá errado). Use espaços, nunca TAB.

Depois de mudar o pubspec.yaml, rode flutter pub get para o Flutter baixar o que mudou (os editores fazem isso sozinhos ao salvar).

4. Os outros arquivos da raiz

pubspec.lock

Enquanto o pubspec.yaml diz "quero o cupertino_icons 1.0.8 ou mais novo", o pubspec.lock ("trava") anota a versão exata que foi baixada, e a de cada pacote que esses pacotes usam. Assim, quem baixar o projeto em outro computador recebe as mesmas versões. É gerado pelo pub get: não edite à mão.

test/widget_test.dart

Um teste automático que vem pronto: ele abre o app contador, toca no + e confere se o número virou 1. Na máquina da Ana:

$ flutter test
00:00 +0: loading /home/ana/receitas_da_ana/test/widget_test.dart
00:00 +0: Counter increments smoke test
00:01 +1: All tests passed!

"Carregando o arquivo de teste; rodando o teste Counter increments smoke test ("o contador aumenta"); +1: todos os testes passaram!". O +1 é o número de testes que passaram. Se você trocar o contador por outro app, esse teste vai falhar (ele procura o 0 e o botão +); apague-o ou reescreva-o (aula Testes de Widget).

analysis_options.yaml

$ grep -v "^ *#" analysis_options.yaml | cat -s

include: package:flutter_lints/flutter.yaml

analyzer:
  exclude:
    - build/**
    - android/**
    - ios/**
    - web/**
    - windows/**
    - macos/**
    - linux/**

linter:
  rules:
include: package:flutter_lints/flutter.yaml
Liga o conjunto de regras recomendadas para Flutter (o pacote flutter_lints do pubspec.yaml). São elas que fazem o editor sublinhar, por exemplo, um print esquecido no código.
analyzer: exclude:
Pastas que o analisador não confere: o build e as pastas das plataformas.
linter: rules:
Aqui você liga ou desliga regras uma a uma. Vem vazio.

.gitignore

Se você guarda o projeto no Git (e deveria), este arquivo lista o que não vai para o repositório: tudo o que é gerado, como build/ e .dart_tool/. Assim, o repositório guarda só o que você escreveu.

Um projeto Android, com o Gradle (a ferramenta de compilação do Android: os arquivos .gradle.kts e o gradlew). Em android/app/ ficam a identidade do app (o applicationId), o ícone e o arquivo de permissões (AndroidManifest.xml).
ios/
Um projeto do Xcode: o app de iPhone se chama Runner ("o que roda") por dentro. Só abre num Mac.
web/
A página que carrega o app na web (index.html), o ícone da aba (favicon.png) e o manifest.json, para o site virar "app instalável".
linux/, macos/, windows/
Os projetos de desktop, cada um com as ferramentas do seu sistema.

Você vai entrar nessas pastas só para coisas específicas da plataforma: trocar o ícone, o nome que aparece no celular, pedir permissão de câmera ou de internet. As aulas de build (Gerando o APK e o App Bundle) e de plataforma (Recursos do Aparelho) mostram como.

Não usa uma plataforma?

Pode apagar a pasta dela (por exemplo, windows/). Se um dia precisar de volta, flutter create --platforms windows . dentro do projeto recria só ela (aula Criando um Projeto).

Quando dá errado

Um espaço a menos no pubspec.yaml

A Ana apagou sem querer um dos dois espaços antes do cupertino_icons:

dependencies:
  flutter:
    sdk: flutter

  # The following adds the Cupertino Icons font to your application.
  # Use with the CupertinoIcons class for iOS style icons.
 cupertino_icons: ^1.0.8

$ flutter pub get
Unhandled exception:
Error on line 36, column 2: Expected a key while parsing a block mapping.
   ╷
36 │  cupertino_icons: ^1.0.8
   │  ^
   ╵
#0      Parser._parseBlockMappingKey (package:yaml/src/parser.dart:454:5)
#1      Parser._stateMachine (package:yaml/src/parser.dart:100:16)
#2      Parser.parse (package:yaml/src/parser.dart:61:19)
«  ... mais 19 linhas de rastro, #3 a #21, de dentro do flutter_tools
#21     main (package:flutter_tools/executable.dart:103:3)
<asynchronous suspension>

Parece assustador, mas só as primeiras linhas interessam:

Unhandled exception:
"Exceção não tratada": o próprio comando flutter quebrou ao ler o arquivo.
Error on line 36, column 2:
O lugar do erro no pubspec.yaml: linha 36, coluna 2 (as linhas de comentário contam).
Expected a key while parsing a block mapping.
"Esperava uma chave ao ler um bloco de mapeamento." Tradução livre: "esta linha não está alinhada com nenhum bloco". Com 1 espaço, o cupertino_icons não ficou nem dentro do dependencies (que pede 2) nem fora dele (0).
a linha 36 e o ^
A linha problemática, com o ^ embaixo da coluna 2.
#0, #1, #2...
O rastro (stack trace): o caminho que o código do flutter fez até o erro. É útil para quem programa o Flutter, não para você. Pode ignorar.

Como consertar: volte a indentação para 2 espaços, alinhada com o flutter: de cima, e rode flutter pub get de novo.

Código fora da lib

Um arquivo receita.dart salvo na raiz do projeto não pode ser importado pelo app com package:receitas_da_ana/receita.dart: esse caminho sempre começa na pasta lib. Como consertar: mova o arquivo para dentro de lib/.

Apagou o pubspec.lock ou o .dart_tool

Sem problema: são gerados. Um flutter pub get cria tudo de novo.

Resumo

  • No dia a dia, você mexe em lib/ (o código, começando no main.dart) e no pubspec.yaml (a ficha).
  • O pubspec.yaml tem o nome, a versão (1.0.0+1), a versão do Dart e os pacotes (dependencies e dev_dependencies). Depois de mudar, flutter pub get.
  • No YAML, a indentação manda: um espaço a menos quebra o arquivo.
  • pubspec.lock, .dart_tool/ e build/ são gerados; não edite.
  • test/ guarda os testes; o analysis_options.yaml, as regras do analisador.
  • android/, ios/, web/ e as de desktop são os projetos nativos: você entra nelas só para ícone, nome e permissões.
