Flutter Riverpod

O Riverpod foi criado pelo mesmo autor do provider, para resolver os incômodos dele. O nome é um anagrama de "provider" (as mesmas letras, em outra ordem). A grande diferença: no provider, o estado mora dentro da árvore de widgets e é achado pelo tipo; no Riverpod, cada estado é uma variável global, que qualquer widget acha pelo nome, sem depender de onde está na árvore. Isso acaba com o ProviderNotFoundException e deixa o compilador conferir mais coisas por você.

Você vai aprender
  • A instalar o flutter_riverpod e ligar o Riverpod com ProviderScope.
  • A declarar um provider simples (Provider) e um com estado que muda (Notifier + NotifierProvider).
  • A ler o estado com ConsumerWidget, WidgetRef, ref.watch e ref.read.
  • Por que, no Riverpod, a lista do estado é trocada, e não modificada.
  • As diferenças para o provider, e qual escolher.
  • Os erros reais: o ProviderScope esquecido e a tela que não muda.

Versões desta aula: flutter_riverpod 3.4.3, a versão mais nova no pub.dev em outubro de 2026, e o Flutter estável do laboratório da Ana. O Riverpod 3 mudou bastante em relação ao 2: tutoriais antigos usam StateNotifier e StateProvider, que no 3 ficaram num arquivo à parte, o legacy.dart ("legado"). Esta aula usa só o jeito atual.

A ideia: o armário com etiquetas

No provider, o estado era o quadro na porta da geladeira: só alcança quem passa por aquela porta (quem está abaixo do provider na árvore). No Riverpod, pense num armário com gavetas etiquetadas na entrada da casa:

  1. Cada gaveta é um provider, declarado uma vez, com um nome: carrinhoProvider.
  2. O armário é o ProviderScope: é ele que guarda o conteúdo de todas as gavetas. Ele fica em volta do app inteiro.
  3. Qualquer widget abre a gaveta pelo nome: ref.watch(carrinhoProvider). Não importa em que cômodo (tela) ele está.
  4. A gaveta só é aberta (o estado só é criado) quando alguém a pede pela primeira vez.

ProviderScope
O "armário": guarda o estado de todos os providers do app. Sem ele, nenhum provider funciona (veja Quando dá errado).
const
Ele pode ser const: ao contrário do ChangeNotifierProvider, ele não recebe nenhuma função de criar estado. Quem sabe criar o estado são os próprios providers.

2. O provider mais simples: um valor que não muda

final nomeLojaProvider = Provider<String>((ref) => 'Lojinha da Ana');
final nomeLojaProvider
Uma variável global (fora de qualquer classe). Não se assuste: ela não guarda o valor, só a receita de como criá-lo. O valor fica no ProviderScope. Por convenção, o nome termina em Provider.
Provider<String>
Um provider de valor fixo, do tipo String.
(ref) => 'Lojinha da Ana'
A função que cria o valor. O ref serve para um provider ler outros providers (ex.: ref.watch(outroProvider)).

3. Estado que muda: Notifier e NotifierProvider

O carrinho da lojinha, agora em Riverpod. Compare com a classe Carrinho da aula Provider:

class CarrinhoNotifier extends Notifier<List<String>> {
  @override
  List<String> build() => [];

  void adicionar(String item) {
    state = [...state, item];
  }

  void limpar() {
    state = [];
  }
}

final carrinhoProvider =
    NotifierProvider<CarrinhoNotifier, List<String>>(CarrinhoNotifier.new);
extends Notifier<List<String>>
Uma classe que cuida de um estado do tipo List<String>. Ela ganha um campo state ("estado").
List<String> build() => []
O estado inicial: o carrinho começa vazio. O Riverpod chama o build na primeira vez que alguém pede o provider.
state = [...state, item]
Muda o estado: cria uma lista nova, com tudo o que tinha (...state, o operador de espalhar do Dart) mais o item. Ao receber um valor novo, o state avisa sozinho quem está olhando: não existe notifyListeners().
NotifierProvider<CarrinhoNotifier, List<String>>
A "gaveta": liga a classe ao estado. O primeiro tipo é a classe; o segundo, o tipo do estado.
CarrinhoNotifier.new
Uma referência ao construtor da classe (o mesmo que () => CarrinhoNotifier()). O Riverpod chama quando precisar.
Troque, não modifique

O Riverpod percebe a mudança quando state recebe um objeto diferente. Se você fizer state.add(item), a lista é a mesma (só ganhou um item), o Riverpod não percebe, e a tela não muda. Por isso o jeito certo é state = [...state, item]. A seção Quando dá errado mostra o caso.

4. Ler o estado: ConsumerWidget e ref

Para um widget ler providers, ele estende ConsumerWidget no lugar de StatelessWidget. O build ganha um segundo parâmetro, o WidgetRef ref:

import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

class CarrinhoNotifier extends Notifier<List<String>> {
  @override
  List<String> build() => [];

  void adicionar(String item) {
    state = [...state, item];
  }

  void limpar() {
    state = [];
  }
}

final carrinhoProvider =
    NotifierProvider<CarrinhoNotifier, List<String>>(CarrinhoNotifier.new);

final nomeLojaProvider = Provider<String>((ref) => 'Lojinha da Ana');

void main() {
  runApp(const ProviderScope(child: LojinhaApp()));
}

class LojinhaApp extends StatelessWidget {
  const LojinhaApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      debugShowCheckedModeBanner: false,
      home: TelaProdutos(),
    );
  }
}

class TelaProdutos extends ConsumerWidget {
  const TelaProdutos({super.key});

  static const produtos = ['Café', 'Pão de queijo', 'Bolo de cenoura'];

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final nomeLoja = ref.watch(nomeLojaProvider);
    final itens = ref.watch(carrinhoProvider);
    return Scaffold(
      appBar: AppBar(
        title: Text(nomeLoja),
        actions: [
          Padding(
            padding: const EdgeInsets.only(right: 16),
            child: Badge(
              label: Text('${itens.length}'),
              child: const Icon(Icons.shopping_cart),
            ),
          ),
        ],
      ),
      body: ListView(
        children: [
          for (final produto in produtos)
            ListTile(
              title: Text(produto),
              trailing: IconButton(
                icon: const Icon(Icons.add_shopping_cart),
                tooltip: 'Adicionar $produto',
                onPressed: () =>
                    ref.read(carrinhoProvider.notifier).adicionar(produto),
              ),
            ),
        ],
      ),
    );
  }
}
extends ConsumerWidget
Um StatelessWidget que sabe ler providers.
build(BuildContext context, WidgetRef ref)
O ref é a "chave do armário" deste widget.
ref.watch(carrinhoProvider)
Lê o estado (a lista) e fica de olho: quando o state mudar, este build roda de novo. Use no build.
ref.read(carrinhoProvider.notifier)
O .notifier dá acesso à classe (CarrinhoNotifier), e não à lista, para chamar adicionar. O read não fica de olho: é o certo em onPressed.

Repare no título: ele vem do nomeLojaProvider da seção 2, lido com ref.watch(nomeLojaProvider). Um build pode ler quantos providers quiser.

5. Outras formas de ler: Consumer e ConsumerStatefulWidget

Se você não quer transformar a classe inteira em ConsumerWidget, use o widget Consumer, que dá um ref só para um pedaço:

Consumer(
  builder: (context, ref, child) {
    final itens = ref.watch(carrinhoProvider);
    return Text('Itens: ${itens.length}');
  },
)

E se o widget precisa de initState ou de um TextEditingController, há a versão com estado: ConsumerStatefulWidget com ConsumerState. Nela, o ref é um campo da classe (você escreve ref.watch(…) em qualquer método, sem recebê-lo como parâmetro).

Você escrevia…No Riverpod, escreva…
StatelessWidgetConsumerWidget (o build recebe WidgetRef ref)
StatefulWidget + StateConsumerStatefulWidget + ConsumerState
só um pedaço de um buildConsumer(builder: (context, ref, child) => …)

Provider ou Riverpod?

providerRiverpod
Onde mora o estadoNa árvore de widgets, acima de quem usaNo ProviderScope; achado por uma variável global
Como se achaPelo tipo: context.watch<Carrinho>()Pelo nome: ref.watch(carrinhoProvider)
Esqueceu de pôr o estado no lugar certoErro na hora de rodar (ProviderNotFoundException)Não acontece: a gaveta existe sempre
Avisar mudançanotifyListeners()Atribuir um state novo
Dois estados do mesmo tipoDifícil (o tipo é a "chave")Fácil: são duas variáveis
Quantidade de conceitosMenorMaior (e mudou bastante entre as versões 2 e 3)

Qual usar? Para aprender e para apps pequenos e médios, o provider é mais simples e é o que a documentação oficial do Flutter usa no exemplo de estado compartilhado. O Riverpod compensa em apps maiores, com muitos estados que dependem uns dos outros. O importante é escolher um e usá-lo no app inteiro.

Quando dá errado

Esqueceu o ProviderScope

A Ana deixou o main só com runApp(const LojinhaApp());. Desta vez não é um pedacinho: a tela inteira fica vermelha, porque é a TelaProdutos (a tela toda) que lê os providers:

══╡ EXCEPTION CAUGHT BY WIDGETS LIBRARY ╞═══════════════════════════════════════════════════════════
The following StateError was thrown building TelaProdutos(dirty, state: _ConsumerState#ad602):
Bad state: No ProviderScope found
…
EXCEPTION CAUGHT BY WIDGETS LIBRARY
"Exceção capturada pela biblioteca de widgets": o erro aconteceu enquanto o Flutter montava a tela.
StateError was thrown building TelaProdutos
Um StateError ("erro de estado") ao construir a TelaProdutos. O _ConsumerState#ad602 é o estado interno do ConsumerWidget (o número muda a cada execução).
Bad state: No ProviderScope found
"Estado ruim: nenhum ProviderScope encontrado." O ref.watch procurou o "armário" e não achou.

Como consertar: runApp(const ProviderScope(child: LojinhaApp())); e reinicie o app (o main não roda de novo num hot reload).

state.add: a lista muda, a tela não

Quem vem do provider escreve, por hábito, state.add(item):

  void adicionar(String item) {
    state.add(item);
    print('Carrinho: $state');
  }

Depois de dois toques, o console mostra a lista crescendo…

Carrinho: [Café]
Carrinho: [Café, Pão de queijo]

…mas o selo continua em 0, como na foto de "Ao abrir". O add mexeu dentro da mesma lista; o state continua apontando para o mesmo objeto, e o Riverpod só avisa os widgets quando state recebe outro objeto. Não há erro nem aviso. Como consertar: state = [...state, item];. Para tirar um item: state = state.where((i) => i != item).toList();.

}

class TelaProdutos extends ConsumerWidget {
  const TelaProdutos({super.key});

  static const produtos = ['Café', 'Pão de queijo', 'Bolo de cenoura'];

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final nomeLoja = ref.watch(nomeLojaProvider);
    final itens = ref.watch(carrinhoProvider);
    return Scaffold(
      appBar: AppBar(
        title: Text(nomeLoja),
        actions: [
          Padding(
            padding: const EdgeInsets.only(right: 16),
            child: Badge(
              label: Text('${itens.length}'),
              child: const Icon(Icons.shopping_cart),
            ),
          ),
        ],
      ),
      body: ListView(
        children: [
          for (final produto in produtos)
            ListTile(
              title: Text(produto),
              trailing: IconButton(
                icon: const Icon(Icons.add_shopping_cart),
                tooltip: 'Adicionar $produto',
                onPressed: () =>
                    ref.read(carrinhoProvider.notifier).adicionar(produto),
              ),
            ),
        ],
      ),
      bottomNavigationBar: Padding(
        padding: const EdgeInsets.all(16),
        child: Text('Itens: ${itens.join(', ')}'),
      ),
    );
  }
}

Resumo

  • O Riverpod guarda todo o estado num ProviderScope, em volta do app; cada provider é uma variável global com a receita do estado.
  • Estado que muda: uma classe Notifier<T>, com build() para o valor inicial e métodos que atribuem um state novo, mais um NotifierProvider.
  • Widgets que leem providers estendem ConsumerWidget; no build, ref.watch(xProvider); em botões, ref.read(xProvider.notifier).metodo().
  • Troque o estado (state = [...state, item]), não o modifique (state.add).
  • Sem ProviderScope, o primeiro ref.watch dá Bad state: No ProviderScope found e a tela fica vermelha.
