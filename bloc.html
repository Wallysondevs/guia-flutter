Flutter BLoC

BLoC quer dizer Business Logic Component, "componente da lógica do negócio". É um jeito de organizar o app em que a tela nunca mexe no estado diretamente: ela só manda pedidos (eventos) para um objeto, o bloc, e desenha o que ele devolve (estados). É mais cerimonioso que o provider e o Riverpod, e por isso é muito usado em empresas com apps grandes e equipes grandes: todo mundo escreve do mesmo jeito. Esta aula é uma olhada: o suficiente para você reconhecer e escrever o básico.

Você vai aprender
  • A ideia do BLoC: eventos entram, estados saem.
  • O Cubit, a versão simples: métodos que chamam emit.
  • A entregar o cubit para a tela com BlocProvider e desenhar o estado com BlocBuilder.
  • O Bloc "completo", com classes de evento e on<Evento>.
  • O BlocListener, para reagir a um estado sem redesenhar (mostrar um aviso).
  • Os erros reais: o BlocProvider esquecido e o botão que cria um cubit novo a cada toque.

Versões desta aula: flutter_bloc 9.1.1 e bloc 9.2.1, as mais novas no pub.dev em outubro de 2026, e o Flutter estável do laboratório da Ana.

A ideia: o balcão da padaria

Na padaria, o cliente não entra na cozinha para pegar o pão. Ele faz um pedido no balcão ("dois pães, por favor"), e o balconista devolve o resultado (o saquinho com os pães). Quem decide como atender é o balconista; o cliente só pede e recebe.

  1. O cliente é a tela (os widgets).
  2. O pedido é um evento: "toquei no botão de mais".
  3. O balconista é o bloc: recebe o evento, faz a conta, e…
  4. …devolve um estado novo: "agora são 3 pães". A tela desenha o estado.
  tela ──── evento ────▶  bloc  ──── estado ────▶ tela
 (botão +)  "mais um"   (lógica)    3 pães     (Text '3')

A tela não sabe fazer conta nenhuma, e o bloc não sabe nada de botões e cores. Cada lado pode ser trocado ou testado sozinho.

2. O Cubit: o BLoC sem cerimônia

O Cubit é o jeito mais simples: no lugar de classes de evento, a tela chama métodos. Cada método calcula o estado novo e o entrega com emit ("emitir"). O contador de pães:

class PaesCubit extends Cubit<int> {
  PaesCubit() : super(0);

  void mais() => emit(state + 1);
  void menos() {
    if (state > 0) emit(state - 1);
  }
}
extends Cubit<int>
Um cubit cujo estado é um int (a quantidade de pães). O estado pode ser de qualquer tipo: um número, uma lista, uma classe sua.
super(0)
O estado inicial: zero pães.
state
O estado atual, só para leitura. Não dá para escrever state = 3 num cubit: o único jeito de mudar é…
emit(state + 1)
…entregar um estado novo. Quem está olhando o cubit recebe o 1, o 2, o 3…
if (state > 0)
A regra do negócio ("não existe quantidade negativa de pão") mora aqui, no cubit, e não no botão.

3. Na tela: BlocProvider e BlocBuilder

import 'package:flutter/material.dart';
import 'package:flutter_bloc/flutter_bloc.dart';

class PaesCubit extends Cubit<int> {
  PaesCubit() : super(0);

  void mais() => emit(state + 1);
  void menos() {
    if (state > 0) emit(state - 1);
  }
}

void main() {
  runApp(
    BlocProvider(
      create: (context) => PaesCubit(),
      child: const PadariaApp(),
    ),
  );
}

BlocProvider(create: (context) => PaesCubit(), child: …)
Cria o cubit e o entrega para os widgets de baixo, como o ChangeNotifierProvider do provider (por dentro, o flutter_bloc usa mesmo o pacote provider). Ele também fecha o cubit quando sai da árvore.
BlocBuilder<PaesCubit, int>
Fica de olho no cubit e chama o builder a cada estado novo. Os tipos: o cubit e o tipo do estado.
builder: (context, paes) => …
Recebe o estado (aqui, o número de pães) e devolve o widget. Só esse pedaço é redesenhado.
context.read<PaesCubit>().mais()
No botão, a tela pede: "mais um". O mesmo read do provider: pega o cubit sem ficar de olho.
heroTag: 'menos' / 'mais'
Dois FloatingActionButton na mesma tela precisam de heroTag diferentes (o botão flutuante usa um Hero por dentro).

4. O Bloc "completo": eventos de verdade

No Bloc (sem o "Cu"), a tela não chama métodos: ela adiciona eventos, que são objetos. Cada tipo de evento tem um tratador, registrado com on<Evento>:

sealed class PaesEvento {}

class MaisPao extends PaesEvento {}

class MenosPao extends PaesEvento {}

class PaesBloc extends Bloc<PaesEvento, int> {
  PaesBloc() : super(0) {
    on<MaisPao>((evento, emit) => emit(state + 1));
    on<MenosPao>((evento, emit) {
      if (state > 0) emit(state - 1);
    });
  }
}
sealed class PaesEvento
A "família" de eventos deste bloc. O sealed (do Dart 3) avisa o compilador de que não existem outros eventos além dos declarados neste arquivo.
class MaisPao / MenosPao
Os pedidos possíveis. Um evento pode carregar dados (ex.: class AdicionarPaes { final int quantidade; … }).
Bloc<PaesEvento, int>
Dois tipos: o que entra (eventos) e o que sai (estado).
on<MaisPao>((evento, emit) => …)
"Quando chegar um MaisPao, faça isto." O emit chega como parâmetro.

Na tela, só o botão muda: no lugar de context.read<PaesCubit>().mais(), fica

onPressed: () => context.read<PaesBloc>().add(MaisPao()),

e o BlocBuilder vira BlocBuilder<PaesBloc, int>. O resto é igual.

CubitBloc
A tela pede com…um método: cubit.mais()um evento: bloc.add(MaisPao())
CódigoMenosMais (uma classe por evento)
RastreioVê os estadosVê os estados e os eventos que os causaram
Quando usarA maior parte das telasLógica com muitos pedidos, que precisam ser registrados, atrasados ou cancelados (ex.: busca enquanto digita)

5. BlocListener: reagir sem redesenhar

Às vezes um estado novo não deve mudar o desenho, e sim fazer algo uma vez: mostrar um SnackBar, abrir outra tela. Para isso existe o BlocListener ("ouvinte"):

BlocListener<PaesCubit, int>(
  listenWhen: (antes, agora) => agora == 12,
  listener: (context, paes) {
    ScaffoldMessenger.of(context).showSnackBar(
      const SnackBar(content: Text('Uma dúzia! Ganhou um sonho de brinde.')),
    );
  },
  child: const TelaPaes(),
)
listenWhen
Opcional: só chama o listener quando a função devolver true. Aqui, quando chegar a 12.
listener
Roda uma vez por estado novo. Não devolve widget.

Quando precisa das duas coisas (redesenhar e reagir), há o BlocConsumer, que junta builder e listener.

BLoC, provider ou Riverpod?

SituaçãoSugestão
Estado de um widget só (um campo aberto, uma aba)setState
App pequeno ou médio, aprendendoprovider
App maior, muitos estados que dependem uns dos outrosRiverpod
Equipe grande, regra de negócio pesada, quer separar bem tela e lógicaBLoC (Cubit na maior parte; Bloc onde os eventos importam)

Os três resolvem o mesmo problema. A pior escolha é misturar os três no mesmo app sem motivo.

Quando dá errado

Esqueceu o BlocProvider

A Ana deixou o main só com runApp(const PadariaApp());. O BlocBuilder procura um PaesCubit acima dele e não acha:

The following ProviderNotFoundException was thrown building KeyedSubtree-[GlobalKey#41dda]:
Error: Could not find the correct Provider<PaesCubit> above this BlocBuilder<PaesCubit, int> Widget

This happens because you used a `BuildContext` that does not include the provider
of your choice. There are a few common scenarios:
…
  Make sure that BlocBuilder<PaesCubit, int> is under your MultiProvider/Provider<PaesCubit>.
…

É a mesma ProviderNotFoundException da aula Provider (lá está a explicação linha por linha), porque o flutter_bloc usa o provider por dentro. Ela fala em Provider<PaesCubit>, mas o que falta é o seu BlocProvider. O KeyedSubtree-[GlobalKey#41dda] é um widget interno onde o erro estourou (o número muda a cada execução); o que interessa é o fim da linha seguinte: above this BlocBuilder<PaesCubit, int> Widget. Como consertar: envolva o app com BlocProvider(create: (context) => PaesCubit(), child: …) e reinicie.

O botão cria um cubit novo a cada toque

Quem esquece o context.read escreve, no botão de mais:

            onPressed: () => PaesCubit().mais(),

Compila, roda, não dá erro… e o número não sai do zero:

PaesCubit() cria um cubit novo, que nasce com 0, vira 1 e é jogado fora. O BlocBuilder está olhando outro cubit, o que o BlocProvider criou, e esse ninguém mudou. Como consertar: peça o cubit que já existe: context.read<PaesCubit>().mais().

Missão: rode e toque no +: o número não muda (o − funciona, mas não há o que tirar). Conserte o botão de mais.

Um emit com o mesmo estado é ignorado

O emit compara o estado novo com o atual (com ==) e, se forem iguais, não faz nada. Com números, é isso que se quer. Com listas, é uma armadilha: state.add(item); emit(state); emite a mesma lista, o == dá true, e a tela não muda (o mesmo problema do state.add na aula Riverpod). Como consertar: emit([...state, item]);.

            child: const Icon(Icons.add),
          ),
        ],
      ),
    );
  }
}

Resumo

  • BLoC separa a tela da lógica: a tela pede (eventos ou métodos), o bloc calcula e entrega estados com emit, a tela desenha.
  • Cubit<T>: métodos que chamam emit. Bloc<Evento, T>: classes de evento tratadas com on<E>.
  • BlocProvider cria e entrega; BlocBuilder redesenha; BlocListener reage uma vez; context.read pede.
  • Um emit com um estado igual ao atual é ignorado: em listas, emita uma lista nova.
