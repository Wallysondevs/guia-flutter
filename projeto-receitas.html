Flutter Projeto: App de Receitas

Quase todo app tem mais de uma tela: a lista de produtos e a página do produto, a caixa de entrada e o e-mail aberto. Neste projeto, a Ana monta o caderno de receitas dela no celular: uma tela com a lista de receitas e, ao tocar numa delas, uma segunda tela com o tempo de preparo e os ingredientes. O app cresce em 3 versões, cada uma com o código completo, a foto real e uma missão no editor.

Você vai aprender
  • Versão 1: organizar os dados numa classe de modelo (Receita) e mostrar a lista com Card e ListTile.
  • Versão 2: abrir a tela de detalhe com Navigator.push e MaterialPageRoute, passando a receita pelo construtor.
  • Versão 3: voltar com uma resposta, usando Navigator.pop(context, valor), e mostrar um SnackBar na tela da lista.
  • O erro real "Navigator operation requested with a context that does not include a Navigator", e como resolver.

Aulas que ajudam: Indo de uma Tela para Outra, Passando Dados entre Telas, Card e ListTile, ListView.builder e Diálogos e SnackBar.

O plano: duas telas e uma pilha

Pense numa pilha de pratos. Quando o app abre, a lista de receitas é o primeiro prato. Tocar numa receita põe um prato em cima (a tela de detalhe): é o push ("empurrar"). A seta de voltar tira o prato de cima e a lista reaparece, do jeito que estava: é o pop ("tirar"). O Navigator do Flutter é exatamente essa pilha de telas.

ReceitasApp (MaterialApp, que cria o Navigator)
│
├── tela 1: ListaPage (Scaffold)
│   └── ListView.builder → Card → ListTile (uma por receita)
│          │  toque: Navigator.push(…)
│          ▼
└── tela 2: DetalhePage(receita: …) (Scaffold)
    └── ListView: tempo, 'Ingredientes', um ListTile por ingrediente,
                  botão 'Fiz esta receita!' → Navigator.pop(context, nome)

Versão 1: a lista de receitas

Cada receita tem um nome, um tempo de preparo e uma lista de ingredientes. Em vez de espalhar isso em várias listas, tudo fica junto numa classe Receita, e as receitas da Ana ficam numa lista constante no alto do arquivo.

import 'package:flutter/material.dart';

void main() => runApp(const ReceitasApp());

class Receita {
  const Receita({
    required this.nome,
    required this.minutos,
    required this.ingredientes,
  });

  final String nome;
  final int minutos;
  final List<String> ingredientes;
}

const receitas = [
  Receita(
    nome: 'Bolo de cenoura',
    minutos: 50,
    ingredientes: ['3 cenouras', '4 ovos', '1 xícara de óleo', '2 xícaras de açúcar', '2 xícaras de farinha'],
  ),
  Receita(
    nome: 'Brigadeiro',
    minutos: 20,
    ingredientes: ['1 lata de leite condensado', '1 colher de manteiga', '3 colheres de chocolate em pó'],
  ),
  Receita(
    nome: 'Pão de queijo',
    minutos: 40,
    ingredientes: ['500 g de polvilho', '2 ovos', '1 xícara de leite', '200 g de queijo'],
  ),
];

class ReceitasApp extends StatelessWidget {
  const ReceitasApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Receitas da Ana',
      debugShowCheckedModeBanner: false,

    );
  }

  Widget build(BuildContext context) {

          );
        },
      ),
    );
  }
}
class Receita { const Receita({required this.nome, …}); … }
A classe de modelo. Os campos são final (uma receita não muda depois de criada) e o construtor é const, o que permite criar as receitas como constantes. Os parâmetros são nomeados e obrigatórios (required): ninguém esquece o tempo de preparo.
const receitas = [ Receita(…), … ];
Os dados do app: uma lista constante, fora de qualquer widget. Num app real, eles viriam da internet ou de um banco de dados (veja http e sqflite); aqui, a lista fixa deixa o foco na navegação.
final receita = receitas[index];
Dentro do itemBuilder, pega a receita daquela linha. Daqui para baixo, receita.nome é mais claro do que receitas[index].nome repetido.
Card(margin: …, child: ListTile(…))
Cada receita num cartão, com 16 pixels dos lados e 6 entre um cartão e outro.
subtitle: Text('${receita.minutos} min · ${receita.ingredientes.length} ingredientes')
A segunda linha, menor, com o tempo e a quantidade de ingredientes, montada com interpolação.
trailing: const Icon(Icons.chevron_right)
A setinha à direita: o sinal visual de "toque aqui para abrir". Por enquanto, tocar não faz nada.

A semente laranja (Colors.orange) deu ao app um fundo levemente rosado e cartões cor de pêssego. Cada cartão tem o ícone restaurant_menu (garfo e faca), o nome, a linha de baixo com o tempo e a contagem de ingredientes (calculada com ingredientes.length: ninguém escreveu "5 ingredientes" à mão) e a setinha à direita.

Missão: acrescente uma quarta receita à lista: Receita(nome: 'Pudim', minutos: 60, ingredientes: [...]), com os ingredientes que quiser. Repare que a contagem de ingredientes na segunda linha aparece sozinha.

Versão 2: tocar e abrir o detalhe

Agora cada cartão abre uma segunda tela, a DetalhePage, que recebe a receita tocada pelo construtor, como qualquer parâmetro de widget. Em relação à versão 1, mudaram duas coisas: o onTap no ListTile e a classe nova no fim do arquivo.

onTap: () { Navigator.push(…); }
O que acontece no toque: pôr uma tela nova em cima da pilha.
Navigator.push(context, …)
O context diz ao Flutter onde você está na árvore; a partir dele, o Navigator mais próximo (o que o MaterialApp criou) é encontrado.
MaterialPageRoute(builder: (context) => DetalhePage(receita: receita))
A "rota": o pacote que leva a tela nova, com a animação de entrada padrão do Android (ou do iPhone, no iOS). O builder é uma função que constrói a tela quando for a hora.
class DetalhePage … final Receita receita;
A tela de detalhe guarda a receita que recebeu num campo final, e o build usa esse campo. É assim que dados passam de uma tela para a próxima (veja Passando Dados entre Telas).
final textos = Theme.of(context).textTheme;
Os estilos de texto do tema (titleMedium, titleLarge…). Usar o tema em vez de tamanhos fixos deixa o app coerente (veja Temas).
appBar: AppBar(title: Text(receita.nome))
O título da barra é o nome da receita. Repare que você não escreveu a seta de voltar: a AppBar percebe que há uma tela embaixo na pilha e põe a seta sozinha. Tocar nela faz o pop.
for (final item in receita.ingredientes) ListTile(…)
Um for dentro da lista children (o "collection for" do Dart): gera um ListTile por ingrediente.

No lab, a foto foi tirada depois de um clique no cartão "Bolo de cenoura" (e uma pequena espera, para a animação de entrada terminar). A tela nova cobriu a lista inteira. No alto, a seta de voltar que ninguém programou, e o título com o nome da receita recebida. O tempo usa o estilo titleMedium e "Ingredientes" o titleLarge, maior: as duas medidas vêm do tema.

Missão: na tela de detalhe, troque o ícone de cada ingrediente (Icons.check_circle_outline) por uma cestinha de compras: Icons.shopping_basket. Toque numa receita para ver o detalhe e use a seta para voltar.

Versão 3: voltar com uma resposta

A Ana quer marcar as receitas que já fez. Na tela de detalhe entra um botão Fiz esta receita!, que fecha a tela e leva uma resposta de volta: o nome da receita. A lista recebe essa resposta e mostra um aviso no rodapé, o SnackBar.

}

onPressed: () => Navigator.pop(context, receita.nome)
Tira a tela de detalhe da pilha e entrega um valor a quem a abriu. O segundo argumento do pop é a resposta.
onTap: () async { final feita = await Navigator.push<String>(…); … }
O push devolve um Future: uma promessa de resposta, que só chega quando a tela de cima sair. O await espera por ela (por isso o async). O <String> diz o tipo da resposta esperada. Mais sobre Future em FutureBuilder.
if (feita == null || !context.mounted) return;
Duas proteções. Se a pessoa voltou pela seta, e não pelo botão, a resposta é null: não há o que avisar. E o context.mounted confere se a tela da lista ainda existe depois da espera, uma boa prática sempre que se usa o context depois de um await.
ScaffoldMessenger.of(context).showSnackBar(SnackBar(…))
Mostra o aviso no rodapé da tela, que some sozinho depois de alguns segundos (veja Diálogos e SnackBar).

Formas diferentes de fazer

Navigator.push com a rota, ou rotas nomeadas?

Aqui, a tela nova é criada na hora, com MaterialPageRoute. Outra forma é dar nomes às telas no MaterialApp e navegar pelo nome:

MaterialApp(
  routes: {
    '/': (context) => const ListaPage(),
    '/sobre': (context) => const SobrePage(),
  },
);

// em algum botão:
Navigator.pushNamed(context, '/sobre');

Qual usar: para passar um objeto (como a Receita), o push com MaterialPageRoute é o mais simples e já vem com a checagem de tipos do Dart. Rotas nomeadas ajudam quando o app tem muitas telas fixas, e o pacote go_router é o caminho para apps maiores e para a web, com endereços de verdade (veja Rotas Nomeadas e go_router).

A seta da AppBar ou um botão seu?

Para só voltar, a seta automática basta. Um botão próprio com Navigator.pop(context) faz o mesmo, e com Navigator.pop(context, valor) ainda leva uma resposta, como na versão 3. No Android, o botão "voltar" do sistema também faz pop (e devolve null).

EXCEPTION CAUGHT BY GESTURE
"Exceção capturada pelos gestos": o erro aconteceu enquanto o Flutter tratava um toque.
Navigator operation requested with a context that does not include a Navigator.
"Pediram uma operação de navegação com um context que não tem um Navigator." O Navigator.push(context, …) procura um Navigator acima do context na árvore e não achou nenhum.
must be that of a widget that is a descendant of a Navigator widget
"O context precisa ser de um widget que esteja abaixo de um Navigator." Aqui está a pista: o context usado é o do build do ReceitasApp, que fica acima do MaterialApp, e é o MaterialApp que cria o Navigator.
#3 ReceitasApp.build.<anonymous closure> (package:app/main.dart:18:23)
A primeira linha da pilha que é do seu código: a função anônima (o onTap) dentro do build do ReceitasApp, linha 18, onde está o Navigator.push. As linhas #0 a #2 são do Flutter; procure sempre a primeira com main.dart.
Handler: "onTap"
Qual tratador de gesto estava rodando: o onTap.

Como resolver: separe a tela num widget próprio (a ListaPage das versões acima). O build dela recebe um context que fica abaixo do MaterialApp, e lá o Navigator existe. Outra saída é envolver o ListTile num Builder, que cria um context novo naquele ponto; mas o widget separado é mais claro.

Resumo

  • O Navigator é uma pilha de telas: push põe uma tela em cima, pop tira.
  • Navigator.push(context, MaterialPageRoute(builder: (context) => Tela(…))) abre uma tela; os dados vão pelo construtor dela.
  • A AppBar põe a seta de voltar sozinha quando há tela embaixo.
  • Navigator.pop(context, valor) volta com uma resposta; quem abriu recebe com await, e recebe null se a pessoa voltou pela seta.
  • Depois de um await, confira context.mounted antes de usar o context.
  • O context do mesmo build que cria o MaterialApp não enxerga o Navigator: separe as telas em widgets próprios.
