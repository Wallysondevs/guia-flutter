Flutter Gerando o APK e o App Bundle

Até aqui, o app de compras da Ana só rodou com flutter run, ligado ao computador. Para a mãe dela instalar no celular, ou para publicar na Google Play, é preciso empacotar o app num arquivo: o APK (o instalador do Android) ou o App Bundle (.aab, o formato que a Play Store pede). Esta aula mostra os dois comandos, o que sai de cada um, quanto demora, quanto pesa, e como dar nome, versão e assinatura ao app.

Você vai aprender
  • A diferença entre o modo debug (o do flutter run) e o release (o que vai para as pessoas).
  • Como gerar o APK com flutter build apk, onde ele fica e como instalar.
  • O APK "gordo" e o --split-per-abi (um APK por tipo de processador).
  • Como gerar o App Bundle para a Play Store com flutter build appbundle.
  • Onde mudar o nome do app, o identificador (applicationId) e a versão.
  • Como assinar o app com a sua própria chave (keystore).
  • Os erros mais comuns ao compilar.

As saídas desta página vieram do Flutter 3.47.7 da máquina da Ana (Linux, com o Android SDK e o Java 21 instalados), compilando o app de compras da aula Testes de Widget. Os tempos são os dela: no seu computador serão outros.

A ideia: da cozinha para a marmita

Enquanto a Ana cozinha, ela prova a comida direto da panela, mexe, acerta o sal, prova de novo. É o modo debug: o app ligado ao computador, com hot reload, mensagens de erro detalhadas e a faixa "DEBUG" no canto. Quando a comida fica pronta, ela monta a marmita: fecha bem, etiqueta com o nome e a data, e entrega. É o modo release: o app compilado de verdade, otimizado, mais rápido e menor, sem ferramentas de cozinha dentro. Ninguém entrega a panela.

Instalando o APK

Há dois jeitos:

  • Pelo cabo, com o celular ligado e a depuração USB ativada: flutter install (instala o release que acabou de ser gerado) ou adb install build/app/outputs/flutter-apk/app-release.apk.
  • Mandando o arquivo (por e-mail, Drive, mensageiro): no celular, a pessoa toca no APK e permite "instalar apps desconhecidos" para aquele aplicativo. O Android mostra um aviso, porque o app não veio da loja.

2. Por que 48 MB? O --split-per-abi

Os celulares Android usam processadores de tipos diferentes, as ABIs: arm64-v8a (quase todos os celulares atuais), armeabi-v7a (os mais antigos, de 32 bits) e x86_64 (emuladores e alguns tablets). O APK padrão é gordo (fat APK): leva o app compilado para os três, e cada celular usa só um. Para separar:

$ flutter build apk --split-per-abi
Running Gradle task 'assembleRelease'...                           19.4s
✓ Built build/app/outputs/flutter-apk/app-armeabi-v7a-release.apk (14.1MB)
✓ Built build/app/outputs/flutter-apk/app-arm64-v8a-release.apk (16.7MB)
✓ Built build/app/outputs/flutter-apk/app-x86_64-release.apk (18.2MB)

Três APKs, cada um com um terço do tamanho. Some os três: 14,1 + 16,7 + 18,2 = 49,0 MB, praticamente o APK gordo. Para mandar para um celular moderno, o app-arm64-v8a-release.apk basta.

Qual usar

APK gordo: para mandar a alguém sem se preocupar com o tipo do celular (funciona em todos). Split: quando o tamanho importa e você sabe o aparelho. App Bundle (próxima seção): para a Play Store, que faz essa separação sozinha.

3. Para a Play Store: flutter build appbundle

A Google Play não aceita APK para apps novos: ela pede o App Bundle (.aab). Você envia o pacote completo, e a própria loja monta, para cada celular, um APK só com o que ele precisa (a ABI dele, as imagens na resolução da tela dele).

$ flutter build appbundle
Running Gradle task 'bundleRelease'...                             20.3s
✓ Built build/app/outputs/bundle/release/app-release.aab (47.4MB)

O .aab tem quase o tamanho do APK gordo, mas o que cada pessoa baixa da loja é bem menor. O .aab não instala direto no celular: ele é só para enviar à loja. O envio está na aula Publicando nas Lojas.

4. Nome, identificador e versão

O app ainda se chama compras e tem o identificador com.example.compras. Antes de entregar a alguém, acerte três coisas.

O nome que aparece embaixo do ícone

    <application
        android:label="Compras da Ana"
        android:name="${applicationName}"
        android:icon="@mipmap/ic_launcher">

Troque o android:label (no projeto novo, ele vem com o nome da pasta, compras). O ícone é o @mipmap/ic_launcher, as imagens em android/app/src/main/res/mipmap-*. O jeito mais prático de trocar é o pacote flutter_launcher_icons, que gera todos os tamanhos a partir de uma imagem (veja Pacotes).

O identificador (applicationId)

É o "CPF" do app: a Play Store e o celular reconhecem o app por ele, e ele nunca mais pode mudar depois de publicado. O projeto novo vem com um aviso TODO ("a fazer"):

    defaultConfig {
        // TODO: Specify your own unique Application ID (https://developer.android.com/studio/build/application-id.html).
        applicationId = "com.example.compras"
        // You can update the following values to match your application needs.
        // For more information, see: https://flutter.dev/to/review-gradle-config.
        minSdk = flutter.minSdkVersion
        targetSdk = flutter.targetSdkVersion
        …
        versionCode = flutter.versionCode
        versionName = flutter.versionName
    }

"Especifique o seu próprio ID de aplicativo, único." O costume é usar um domínio seu ao contrário: br.com.anasilva.compras. O com.example é recusado pela Play Store.

A versão

O versionCode e o versionName vêm do pubspec.yaml:

version: 1.0.0+1
1.0.0
O versionName: o que as pessoas veem na loja ("versão 1.0.0").
+1
O versionCode: um número inteiro que a loja usa para saber qual é mais novo. A cada envio à Play Store ele tem de aumentar (1.0.1+2, 1.1.0+3…).

Também dá para passar na hora, sem mexer no arquivo: flutter build appbundle --build-name=1.0.1 --build-number=2.

5. Assinatura: a sua chave

Todo app Android é assinado com uma chave digital, que prova que as atualizações vêm do mesmo autor. Repare no fim do build.gradle.kts gerado:

    buildTypes {
        release {
            // TODO: Add your own signing config for the release build.
            // Signing with the debug keys for now, so `flutter run --release` works.
            signingConfig = signingConfigs.getByName("debug")
        }
    }

"Adicione a sua própria configuração de assinatura. Por enquanto, assinando com as chaves de debug." Ou seja: os APKs acima foram assinados com a chave de debug, que o Android SDK cria sozinho em cada computador. Servem para testar e mandar para a família, mas não para a Play Store. Para publicar, siga os passos da documentação oficial (docs.flutter.dev/deployment/android), resumidos aqui (ilustrativo):

  1. Crie a chave com o keytool (vem com o Java): 
    $ keytool -genkey -v -keystore ~/upload-keystore.jks -keyalg RSA \
    -keysize 2048 -validity 10000 -alias upload
    Ele pergunta uma senha e seus dados. Guarde o arquivo .jks e a senha num lugar seguro: sem eles, você não consegue mais atualizar o app (a Play Store tem um processo para trocar a chave de envio, mas é trabalhoso).
  2. Crie o arquivo android/key.properties com a senha e o caminho: 
    storePassword=SUA-SENHA
keyPassword=SUA-SENHA
keyAlias=upload
storeFile=/home/ana/upload-keystore.jks
  3. Leia esse arquivo no build.gradle.kts e troque o signingConfigs.getByName("debug") por uma configuração release que use esses dados (o código exato está na documentação).
  4. Nunca envie o key.properties nem o .jks para o Git: ponha os dois no .gitignore.

6. Antes de gerar: confira

Missão: no app de release a faixa "DEBUG" já some sozinha, mas muita gente quer tirá-la também das capturas de tela feitas em debug. Acrescente debugShowCheckedModeBanner: false ao MaterialApp e rode: a faixa vermelha do canto desaparece.

import 'package:flutter/material.dart';

void main() => runApp(const AppCompras());

class AppCompras extends StatelessWidget {
  const AppCompras({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Compras da Ana',
      home: Scaffold(
        appBar: AppBar(title: const Text('Compras da Ana')),
        body: const Center(child: Text('Versão 1.0.0')),
      ),
    );
  }
}

import 'package:flutter/material.dart';

void main() => runApp(const AppCompras());

class AppCompras extends StatelessWidget {
  const AppCompras({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Compras da Ana',
      debugShowCheckedModeBanner: false,
      home: Scaffold(
        appBar: AppBar(title: const Text('Compras da Ana')),
        body: const Center(child: Text('Versão 1.0.0')),
      ),
    );
  }
}

A lista da Ana antes de cada versão:

  • flutter analyze sem problemas e flutter test passando (veja Testes de Widget).
  • Testou o app em modo release no celular: flutter run --release.
  • Aumentou o version do pubspec.yaml.
  • Nome, ícone e applicationId definitivos.
  • Se o app usa a internet, a permissão <uses-permission android:name="android.permission.INTERNET"/> no AndroidManifest.xml de main (em debug ela vem de outro manifesto; no release, se faltar, o app simplesmente não acessa a rede).

Quando dá errado

No Android SDK found 
$ flutter build apk
[!] No Android SDK found. Try setting the ANDROID_HOME environment variable.

"Nenhum Android SDK encontrado. Tente definir a variável de ambiente ANDROID_HOME." O Flutter não achou as ferramentas do Android. Isso acontece quando o SDK foi instalado num lugar fora do padrão, ou não foi instalado. Como resolver: instale o Android Studio (ele traz o SDK) ou aponte o Flutter para a pasta: flutter config --android-sdk /caminho/do/sdk (ou export ANDROID_HOME=/caminho/do/sdk no seu ~/.bashrc). Depois, flutter doctor mostra se ficou tudo certo (veja flutter doctor).

Licenças do Android não aceitas

Se o flutter doctor mostrar Android license status unknown ou Some Android licenses not accepted, o Gradle se recusa a usar o SDK. Como resolver: flutter doctor --android-licenses e responda y a cada licença (ilustrativo).

A primeira compilação demora "uma eternidade"

Os 239,5 segundos da Ana não foram defeito: na primeira vez o Gradle baixa centenas de megabytes. Não interrompa. Se a internet cair no meio, rode de novo: ele continua de onde parou.

A Play Store recusou o arquivo

As causas mais comuns: enviou o .apk em vez do .aab; o applicationId ainda é com.example…; o versionCode não aumentou; o app foi assinado com a chave de debug. Cada uma tem a sua correção nas seções acima.

O app de release abre e fica cinza

Em release, um erro que em debug mostraria a tela vermelha vira uma tela cinza, sem mensagem. Como resolver: rode flutter run --release com o celular no cabo: a mensagem do erro aparece no terminal. Os erros mais comuns estão em Erros Comuns.

Resumo

  • flutter run é debug (a panela); flutter build é release (a marmita): rápido, menor, sem faixa DEBUG.
  • flutter build apk gera o APK em build/app/outputs/flutter-apk/; --split-per-abi separa por processador.
  • flutter build appbundle gera o .aab que a Play Store pede.
  • Nome no AndroidManifest.xml, identificador no build.gradle.kts, versão no pubspec.yaml (1.0.0+1: nome + código).
  • Para publicar, assine com a sua chave (keytool + key.properties) e guarde-a bem.
