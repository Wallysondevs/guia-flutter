Flutter StatelessWidget

Até aqui, a Ana usou widgets prontos: Text, Icon, Scaffold. E escreveu um widget dela desde a primeira aula, o MeuApp, sem entender bem o que era. Agora o app de receitas vai ter uma lista de receitas, todas com a mesma "cara": nome, ícone, tempo. Em vez de copiar e colar o mesmo pedaço de código três vezes, ela vai criar um widget dela, o CartaoReceita, e usá-lo quantas vezes quiser.

Você vai aprender
  • O que é um StatelessWidget (widget "sem estado") e quando usar.
  • As partes de um widget seu: a classe, o construtor, o build e o context.
  • A receber dados pelo construtor, com campos final e required.
  • A reaproveitar o mesmo widget com dados diferentes.
  • Por que um widget é melhor que uma função que devolve widget.
  • Os erros reais: o parâmetro sem required e o campo sem final.

Todos os apps desta aula foram compilados com o Flutter 3.47.7 do laboratório e fotografados numa tela do tamanho de um celular.

A ideia: o carimbo

Pense num carimbo de "Pago" ou de data. Você faz o carimbo uma vez e carimba quantas folhas quiser; num carimbo de data, só troca os números a cada uso. Ninguém desenha o carimbo à mão em cada folha.

Um widget seu é um carimbo de pedaço de tela. Você escreve a classe uma vez (o desenho do carimbo) e a usa quantas vezes quiser, trocando só os dados (o nome da receita, o tempo).

E o "sem estado" (stateless)? Quer dizer que o carimbo, depois de feito, não muda sozinho. Para mudar o que aparece, é preciso carimbar de novo com outros dados. Um widget que muda sozinho, como um contador que sobe a cada toque, é um StatefulWidget (próximo nível: StatefulWidget).

1. A anatomia de um widget seu

Este é o esqueleto que você já viu no MeuApp. Agora com um widget novo, a TelaInicial:

import 'package:flutter/material.dart';

void main() {
  runApp(const MeuApp());
}

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      home: TelaInicial(),
    );
  }
}

class TelaInicial extends StatelessWidget {
  const TelaInicial({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Receitas da Ana')),
      body: const Center(
        child: Text('Nenhuma receita ainda'),
      ),
    );
  }
}
class TelaInicial extends StatelessWidget
Uma classe nova que é um StatelessWidget (o extends do Dart: herda tudo dele). A partir daqui, TelaInicial() pode ir em qualquer lugar que aceite um widget. O nome começa com maiúscula, como toda classe.
const TelaInicial({super.key});
O construtor, com as chaves dos parâmetros com nome. O super.key repassa a key opcional para o StatelessWidget (aula Keys). O const deixa o Flutter reaproveitar o widget.
@override
"Estou substituindo": avisa que o build abaixo substitui o build do StatelessWidget.
Widget build(BuildContext context)
O coração do widget: o método que diz o que desenhar. Ele devolve um Widget (aqui, um Scaffold inteiro). O Flutter chama o build quando o widget entra na tela.
BuildContext context
O "endereço" deste widget na árvore. Serve para perguntar coisas a quem está acima, como o tema: Theme.of(context) (aula Estilos de Texto).
home: TelaInicial()
O MeuApp usa a TelaInicial como tela inicial. Um widget seu dentro de outro widget seu.
MeuApp                (seu)
└── MaterialApp
    └── TelaInicial   (seu)
        └── Scaffold
            ├── AppBar
            │   └── Text('Receitas da Ana')
            └── Center
                └── Text('Nenhuma receita ainda')

2. Recebendo dados: o CartaoReceita

Um carimbo de data precisa dos números. O CartaoReceita precisa do nome e do tempo da receita. Eles chegam pelo construtor e ficam guardados em campos da classe:

import 'package:flutter/material.dart';

void main() {
  runApp(const MeuApp());
}

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('Receitas da Ana')),
        body: const Column(
          children: [
            CartaoReceita(nome: 'Bolo de cenoura', minutos: 50),
            CartaoReceita(nome: 'Pão de queijo', minutos: 35),
            CartaoReceita(nome: 'Brigadeiro', minutos: 20),
          ],
        ),
      ),
    );
  }
}

class CartaoReceita extends StatelessWidget {
  const CartaoReceita({
    super.key,
    required this.nome,
    required this.minutos,
  });

  final String nome;
  final int minutos;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: ListTile(
        leading: const Icon(Icons.cake),
        title: Text(nome),
        subtitle: Text('$minutos minutos'),
      ),
    );
  }
}
final String nome; final int minutos;
Os campos: onde o widget guarda os dados que recebeu. São final ("definitivo"): recebem o valor uma vez, no construtor, e nunca mais mudam. É isso que faz o widget ser "sem estado".
required this.nome
"Obrigatório": quem usa o CartaoReceita tem de passar o nome. O this.nome é o atalho do Dart que guarda o valor recebido direto no campo nome.
CartaoReceita(nome: 'Bolo de cenoura', minutos: 50)
Usando o widget: um "carimbo" com dados. Os parâmetros têm nome, então a ordem não importa.
Text(nome) e Text('$minutos minutos')
Dentro do build, os campos são usados como variáveis comuns. Repare que esses Text não podem ser const: eles dependem de dados que só se sabe quando o widget é criado.
Card e ListTile
Um cartão com sombra e uma "linha de lista" pronta, com ícone à esquerda, título e subtítulo. Eles têm aula própria: Card e ListTile.
const Column(children: [CartaoReceita(...), ...])
Como o construtor do CartaoReceita é const e os dados são fixos, a coluna inteira pode ser const.

Três cartões, um só código. Se a Ana quiser mudar o ícone de todos os cartões, ela muda uma linha, dentro do CartaoReceita.

3. Parâmetro opcional, com valor padrão

Nem todo dado precisa ser obrigatório. A Ana quer marcar algumas receitas como favoritas; as outras, por padrão, não são:

class CartaoReceita extends StatelessWidget {
  const CartaoReceita({
    super.key,
    required this.nome,
    required this.minutos,
    this.favorita = false,
  });

  final String nome;
  final int minutos;
  final bool favorita;

  @override
  Widget build(BuildContext context) {
    return Card(
      child: ListTile(
        leading: const Icon(Icons.cake),
        title: Text(nome),
        subtitle: Text('$minutos minutos'),
        trailing: Icon(
          favorita ? Icons.favorite : Icons.favorite_border,
          color: Colors.red,
        ),
      ),
    );
  }
}
this.favorita = false
Sem required e com um valor padrão: quem não disser nada ganha false.
favorita ? Icons.favorite : Icons.favorite_border
O operador ternário do Dart ("se ... então ... senão"): coração cheio para as favoritas, vazio para as outras.
trailing:
"O que vem no fim": o widget do lado direito do ListTile.

E o uso fica assim (o Bolo de cenoura é favorito; os outros, não):

            CartaoReceita(nome: 'Bolo de cenoura', minutos: 50, favorita: true),
            CartaoReceita(nome: 'Pão de queijo', minutos: 35),
            CartaoReceita(nome: 'Brigadeiro', minutos: 20),

Formas diferentes: widget ou função?

Quem vem de outras linguagens costuma separar pedaços de tela em funções:

// Jeito 1: uma função que devolve um widget
Widget cartaoReceita(String nome, int minutos) {
  return Card(
    child: ListTile(title: Text(nome), subtitle: Text('$minutos minutos')),
  );
}

// Jeito 2: um widget (o desta aula)
class CartaoReceita extends StatelessWidget {
  ...
}

As duas desenham a mesma coisa. Mas a documentação do Flutter recomenda o widget, e por bons motivos:

FunçãoStatelessWidget
Pode ser constNãoSim: o Flutter pula a reconstrução de widgets const
Tem o próprio contextNão (usa o de quem chamou)Sim: Theme.of(context) funciona como esperado
Aparece na árvore e no DevToolsNão: os widgets de dentro aparecem soltosSim, com o nome dele (aula DevTools)
Quando usarPedaços minúsculos, usados uma vez, dentro do mesmo buildQuase sempre, principalmente o que se repete
Quando criar um widget novo?

Quando um pedaço se repete (os cartões), quando o build passa de uma tela de altura, ou quando um pedaço tem um nome natural ("cartão de receita", "cabeçalho do perfil"). Widgets pequenos, com nomes claros, deixam o código fácil de ler e o app mais rápido.

Quando dá errado

Os dois erros abaixo são de compilação (o app nem abre) e aparecem no CartaoReceita da seção 2, cujo construtor começa na linha 28.

O parâmetro sem required 
  const CartaoReceita({
    super.key,
    this.nome,
    required this.minutos,
  });

  final String nome;

lib/main.dart:30:10: Error: The parameter 'nome' can't have a value of 'null' because of its type 'String', but the implicit default value is 'null'.
Try adding either an explicit non-'null' default value or the 'required' modifier.
    this.nome,
         ^^^^
The parameter 'nome' can't have a value of 'null' because of its type 'String'
"O parâmetro nome não pode valer null, porque o tipo dele é String" (sem ?, o Dart não aceita null: é a segurança contra nulos).
but the implicit default value is 'null'.
"mas o valor padrão implícito é null": um parâmetro com nome que não é required e não tem valor padrão vale null quando ninguém o passa.
Try adding either an explicit non-'null' default value or the 'required' modifier.
A dica já traz os dois consertos: um valor padrão, ou o required.

Como consertar: required this.nome (o nome é obrigatório), ou this.nome = 'Sem nome' (um padrão), ou, se o nome puder mesmo faltar, final String? nome;.

Um campo sem final 
  const CartaoReceita({
    super.key,
    required this.nome,
    required this.minutos,
  });

  String nome;
  final int minutos;

lib/main.dart:28:9: Error: Constructor is marked 'const' so all fields must be final.
  const CartaoReceita({
        ^
lib/main.dart:34:10: Context: Field isn't final, but constructor is 'const'.
  String nome;
         ^

"O construtor é const, então todos os campos precisam ser final", e a linha de Context aponta o culpado: o campo nome, da linha 34. Um objeto const é congelado: nada nele pode mudar, e um campo sem final poderia. Como consertar: final String nome;. Em widgets, todo campo é final: se um dado precisa mudar com o app rodando, ele é estado, e o lugar dele é num StatefulWidget.

Resumo

  • Um StatelessWidget é um widget seu que não muda sozinho: class X extends StatelessWidget com um build que devolve o que desenhar.
  • Os dados chegam pelo construtor e ficam em campos final; required torna o parâmetro obrigatório, e this.x = valor dá um padrão.
  • O construtor const deixa o Flutter reaproveitar o widget.
  • Prefira widgets a funções que devolvem widgets: podem ser const, têm o próprio context e aparecem no DevTools.
  • Se o pedaço de tela precisa mudar sozinho (contador, campo marcado), é um StatefulWidget.
