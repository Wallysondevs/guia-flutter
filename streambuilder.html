Flutter StreamBuilder

Na aula anterior, o FutureBuilder esperou um dado chegar. Mas muita coisa num app chega aos poucos, sem parar: os segundos de um cronômetro, as mensagens de um chat, a posição do motoboy no mapa, os pedidos que entram no balcão da padaria. Para isso o Dart tem o Stream ("fluxo", "correnteza"), e o Flutter tem o StreamBuilder: um widget que redesenha a tela a cada valor novo que passa pela correnteza.

Você vai aprender
  • A diferença entre Future (um valor, uma vez) e Stream (vários valores, ao longo do tempo).
  • Como criar um Stream com async* e yield, e mostrá-lo com StreamBuilder.
  • Os estados de um Stream: waiting, active e done.
  • Como mandar valores para um Stream quando você quiser, com StreamController, e por que fechá-lo no dispose.
  • O erro real Bad state: Stream has already been listened to. e como resolver com .broadcast().

Os exemplos rodaram no laboratório do guia, com o Flutter 3.47. As fotos foram tiradas com o app aberto num navegador do tamanho de um celular.

A ideia: a esteira da padaria

O Future é a senha da padaria: você espera, e chega um bolo. O Stream é a esteira que sai do forno: os pães vão passando, um de cada vez, e não se sabe quando vem o próximo. Quem fica na ponta da esteira (o StreamBuilder) pega cada pão que chega e põe na vitrine (redesenha a tela). Um dia o forno desliga, e a esteira para: o Stream terminou.

1. Uma contagem regressiva com StreamBuilder

O bolo da Ana tem 5 segundos de forno (é um forno muito bom). A tela mostra quanto falta e, no fim, avisa que ficou pronto:

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      debugShowCheckedModeBanner: false,
      home: TelaForno(),
    );
  }
}

// Um Stream que manda 5, 4, 3, 2, 1, 0: um número por segundo.
Stream<int> contagemDoForno() async* {
  for (var segundos = 5; segundos >= 0; segundos--) {
    yield segundos;
    await Future.delayed(const Duration(seconds: 1));
  }
}

class TelaForno extends StatefulWidget {
  const TelaForno({super.key});

  @override
  State<TelaForno> createState() => _TelaFornoState();
}

class _TelaFornoState extends State<TelaForno> {
  late final Stream<int> _contagem;

  @override
  void initState() {
    super.initState();
    _contagem = contagemDoForno();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Forno da Ana')),
      body: Center(
        child: StreamBuilder<int>(
          stream: _contagem,
          builder: (context, snapshot) {
            if (snapshot.hasError) {
              return Text('Erro: ${snapshot.error}');
            }
            switch (snapshot.connectionState) {
              case ConnectionState.none:
              case ConnectionState.waiting:
                return const CircularProgressIndicator();
              case ConnectionState.active:
                return Text(
                  'Faltam ${snapshot.data} s',
                  style: const TextStyle(fontSize: 40),
                );
              case ConnectionState.done:
                return const Text(
                  'Bolo pronto!',
                  style: TextStyle(fontSize: 40, color: Colors.brown),
                );
            }
          },
        ),
      ),
    );
  }
}
Stream<int> contagemDoForno() async*
Uma função geradora. O async* (com estrela) diz que ela devolve um Stream, e não um Future.
yield segundos;
"Entrega" (em inglês, yield) um valor na esteira, e a função continua rodando. No async comum, o return entrega um valor e acaba; no async*, cada yield é mais um valor.
await Future.delayed(const Duration(seconds: 1))
Espera 1 segundo antes do próximo valor. Quando o for acaba, a função termina, e o Stream fica terminado (done).
late final Stream<int> _contagem e initState
Como no FutureBuilder: o Stream é criado uma vez, quando a tela nasce, e guardado num campo.
StreamBuilder<int>(stream: _contagem, builder: …)
Fica "ouvindo" o Stream (os programadores dizem escutar, listen) e chama o builder de novo a cada valor que chega.
switch (snapshot.connectionState)
Os estados de um Stream: waiting (ainda não chegou nada), active (já chegou pelo menos um valor e ainda podem vir mais) e done (o Stream terminou). O none aparece só quando stream é null.
snapshot.data
O último valor que chegou. O StreamBuilder não guarda a lista dos anteriores: só o mais recente.

Repare que o Dart não reclamou de o switch não ter return no fim: o ConnectionState tem exatamente quatro valores, e os quatro estão nos case. O Dart 3 confere isso sozinho (o switch é exaustivo). No laboratório, apagamos o case ConnectionState.done: (e o return dele), e o app parou de compilar:

 - 'ConnectionState' is from 'package:flutter/src/widgets/async.dart'.     « o caminho do arquivo dentro do Flutter foi cortado
Try adding a default case or cases that match 'ConnectionState.done'.
            switch (snapshot.connectionState) {
                             ^

"O tipo ConnectionState não é coberto por inteiro pelos case do switch, porque falta ConnectionState.done." A linha seguinte diz de onde vem o ConnectionState (do próprio Flutter), e a Try adding… sugere o conserto: "tente acrescentar um default ou os case que cubram ConnectionState.done". O ^ aponta o switch da linha 52, coluna 30. É uma ajuda: o Dart não deixa você esquecer um estado.

2. Mandando valores quando quiser: StreamController

Na contagem, a própria função decidia quando mandar cada valor. Muitas vezes, quem decide é outra parte do app: um botão, uma mensagem que chegou da internet. Para isso existe o StreamController ("controlador do fluxo"): uma esteira com uma entrada (add) e uma saída (stream).

import 'dart:async';

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      debugShowCheckedModeBanner: false,
      home: TelaPedidos(),
    );
  }
}

class TelaPedidos extends StatefulWidget {
  const TelaPedidos({super.key});

  @override
  State<TelaPedidos> createState() => _TelaPedidosState();
}

class _TelaPedidosState extends State<TelaPedidos> {
  final _pedidos = StreamController<String>();
  int _numero = 0;

  void _novoPedido() {
    _numero++;
    _pedidos.add('Pedido nº $_numero: bolo de cenoura');
  }

  @override
  void dispose() {
    _pedidos.close();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Pedidos da Padaria')),
      floatingActionButton: FloatingActionButton.extended(
        onPressed: _novoPedido,
        icon: const Icon(Icons.add),
        label: const Text('Novo pedido'),
      ),
      body: Center(
        child: StreamBuilder<String>(
          stream: _pedidos.stream,
          initialData: 'Nenhum pedido ainda',
          builder: (context, snapshot) {
            return Text(
              snapshot.data!,
              style: const TextStyle(fontSize: 22),
            );
          },
        ),
      ),
    );
  }
}
import 'dart:async';
O StreamController mora na biblioteca dart:async do Dart.
final _pedidos = StreamController<String>();
A esteira de pedidos. Ela leva textos (String).
_pedidos.add('Pedido nº …')
A entrada: põe um valor na esteira. Quem estiver escutando recebe.
stream: _pedidos.stream
A saída: o Stream que o StreamBuilder escuta.
initialData: 'Nenhum pedido ainda'
O valor que o snapshot.data tem antes do primeiro pedido. Com ele, snapshot.data! nunca é nulo, e não precisamos da rodinha.
dispose() { _pedidos.close(); … }
Quando a tela sai de cena, feche a esteira. Um StreamController aberto continua guardando quem o escuta, e isso gasta memória à toa (um vazamento de memória). Quem cria o StreamController é responsável por fechá-lo.

Dá para fazer isso só com setState?

Dá: um campo String _ultimo e setState(() => _ultimo = …) no botão. Para um botão na mesma tela, o setState é mais simples e é o que você deve usar. O StreamBuilder vale a pena quando os valores vêm de fora do widget: de um serviço de chat, do banco de dados (o sqflite e o Firebase oferecem Streams), do GPS. O widget só escuta; quem manda está em outro lugar.

Formas diferentes de fazer, e qual usar

Para criar o StreamQuando usar
Função async* com yieldVocê sabe calcular a sequência (contagem, leitura de um arquivo aos pedaços).
Stream.periodic(Duration(seconds: 1), (i) => i)Um valor a cada intervalo fixo, sem fim (relógio). Junte .take(5) para parar depois de 5.
StreamControllerOs valores chegam quando alguém chama add (botões, mensagens, respostas de servidor).
StreamController.broadcast()Mais de um ouvinte ao mesmo tempo (veja Quando dá errado).
Um pacote que já devolve StreamFirebase, sensores, conectividade: você só põe o StreamBuilder.

Linha por linha: The following StateError was thrown building … diz que um erro do tipo StateError ("erro de estado") aconteceu enquanto a tela era montada; Bad state: Stream has already been listened to. quer dizer "estado inválido: este Stream já está sendo escutado". Um StreamController comum aceita um ouvinte só (como um telefone com um fone): o primeiro StreamBuilder pegou o fone, e o segundo quebrou. (Cortamos, no …, o parágrafo sobre "widget creation tracking", que no seu flutter run vira a linha do arquivo com o widget culpado.)

Como consertar: crie o controlador como broadcast ("transmissão", como uma rádio, que qualquer um pode sintonizar): StreamController<String>.broadcast(). Atenção a uma diferença: quem começa a escutar um Stream broadcast depois de um valor ter passado não recebe esse valor; ele só ouve dali em diante. É a missão final desta aula.

Criou o Stream dentro do build

Escrever stream: contagemDoForno() direto no StreamBuilder parece funcionar. Mas toda vez que a tela é reconstruída (um setState qualquer, a tela girando), o build roda de novo, cria outro Stream, e a contagem recomeça do 5. É o mesmo problema do Future criado no build (veja FutureBuilder). Como consertar: crie no initState e guarde num campo.

Esqueceu o close()

Não aparece erro nenhum na tela. O StreamController fica aberto depois que a tela fecha, e o app vai gastando memória. Como evitar: crie o hábito: todo StreamController criado num State tem o seu close() no dispose(), logo abaixo do initState.

Antes do primeiro toque, os dois textos mostram null (Balcão: null): ainda não passou nenhum pedido, e este exemplo não tem initialData. Como você resolveria isso? (Dica: o initialData da seção 2.)

Resumo

  • Um Stream entrega vários valores ao longo do tempo; o StreamBuilder redesenha a tela a cada um.
  • Os estados: waiting (nada ainda), active (chegando valores), done (terminou). O snapshot.data é sempre o último valor.
  • Crie Streams com async* + yield, com Stream.periodic ou com um StreamController (entrada add, saída stream).
  • Crie o Stream no initState (não no build) e feche o StreamController no dispose.
  • Um Stream comum aceita um ouvinte só; para vários, use StreamController.broadcast().
