Flutter Ciclo de Vida

Um State nasce, vive e morre. Ele nasce quando o widget aparece na tela, vive enquanto você toca nos botões e a tela se redesenha, e morre quando o widget sai da tela. Em cada um desses momentos, o Flutter chama um método do seu State. Esse conjunto de momentos se chama ciclo de vida (em inglês, lifecycle), e saber usá-lo é o que separa um app que funciona de um app que fica gastando bateria escondido.

Você vai aprender
  • Os cinco métodos do ciclo de vida: initState, didChangeDependencies, build, didUpdateWidget e dispose.
  • A ordem em que eles rodam, vista no console de um app de verdade.
  • Onde começar as coisas (um Timer, uma busca) e onde terminá-las.
  • O que é o mounted.
  • O erro real setState() called after dispose(), de quem esquece de cancelar o Timer.

As telas e o console desta aula vieram de um Flutter de verdade, no laboratório da Ana, em tamanho de celular.

A ideia: o forno da padaria

Na padaria, cada fornada tem uma rotina:

  1. Ligar o forno uma vez, quando a fornada começa (initState).
  2. Olhar pelo vidro e mostrar ao cliente como está o pão, quantas vezes for preciso (build).
  3. Se o pedido mudar ("agora é pão, não bolo"), ajustar sem desligar o forno (didUpdateWidget).
  4. Desligar o forno quando a fornada acaba (dispose). Esquecer de desligar é desperdício, e pode dar problema.

1. O timer do forno

A Ana fez um painel para a cozinha. Ele mostra um TimerForno, que conta os segundos desde que a receita entrou no forno, e dois botões: um troca a receita para "Pão" e o outro desliga (tira da tela) o timer. Cada método do ciclo de vida escreve no console quando roda:

import 'dart:async';

import 'package:flutter/material.dart';

void main() => runApp(const MeuApp());

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('Cozinha da Ana')),
        body: const Center(child: Painel()),
      ),
    );
  }
}

class Painel extends StatefulWidget {
  const Painel({super.key});

  @override
  State<Painel> createState() => _PainelState();
}

class _PainelState extends State<Painel> {
  bool _ligado = true;
  String _receita = 'Bolo';

  @override
  Widget build(BuildContext context) {
    return Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        if (_ligado) TimerForno(receita: _receita),
        const SizedBox(height: 16),
        FilledButton(
          onPressed: () => setState(() => _receita = 'Pão'),
          child: const Text('Trocar para pão'),
        ),
        OutlinedButton(
          onPressed: () => setState(() => _ligado = !_ligado),
          child: Text(_ligado ? 'Desligar o timer' : 'Ligar o timer'),
        ),
      ],
    );
  }
}

class TimerForno extends StatefulWidget {
  const TimerForno({super.key, required this.receita});

  final String receita;

  @override
  State<TimerForno> createState() => _TimerFornoState();
}

class _TimerFornoState extends State<TimerForno> {
  int _segundos = 0;
  Timer? _timer;

  @override
  void initState() {
    super.initState();
    debugPrint('initState');
    _timer = Timer.periodic(const Duration(seconds: 1), (_) {
      setState(() => _segundos++);
    });
  }

  @override
  void didChangeDependencies() {
    super.didChangeDependencies();
    debugPrint('didChangeDependencies');
  }

  @override
  void didUpdateWidget(TimerForno oldWidget) {
    super.didUpdateWidget(oldWidget);
    debugPrint('didUpdateWidget: ${oldWidget.receita} -> ${widget.receita}');
  }

  @override
  void dispose() {
    debugPrint('dispose');
    _timer?.cancel();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) {
    debugPrint('build: $_segundos s');
    return Text('${widget.receita} no forno: $_segundos s',
        style: const TextStyle(fontSize: 26));
  }
}

Os métodos do ciclo de vida, na ordem em que aparecem no _TimerFornoState:

import 'dart:async';
Traz o Timer, o relógio do Dart que chama uma função de tempos em tempos.
void initState()
"Iniciar o estado." Roda uma vez só, logo que o State é criado, antes do primeiro build. É o lugar de começar as coisas: ligar um Timer, começar uma busca, criar um controlador. A primeira linha tem de ser super.initState();.
Timer.periodic(const Duration(seconds: 1), (_) { … })
Um relógio que chama a função a cada segundo. A função soma 1 em _segundos dentro de um setState, e a tela se redesenha. O (_) é o parâmetro que o Timer passa (ele mesmo), que aqui não usamos.
void didChangeDependencies()
"As dependências mudaram." Roda logo depois do initState e de novo quando algo de que o widget depende muda lá em cima na árvore (o tema, o tamanho da tela, um InheritedWidget). No começo, raramente você vai precisar dele.
void didUpdateWidget(TimerForno oldWidget)
"O widget foi atualizado." Roda quando o pai se redesenha e manda um widget novo, do mesmo tipo, para o mesmo lugar (aqui, com outra receita). O State continua o mesmo; o oldWidget é o widget antigo e o widget é o novo, para você comparar.
void dispose()
"Descartar." Roda uma vez só, quando o widget sai da tela de vez. É o lugar de terminar tudo o que o initState começou: aqui, _timer?.cancel() para o relógio. A última linha tem de ser super.dispose();.
Widget build(BuildContext context)
Roda depois do initState/didChangeDependencies, depois de cada setState e depois de cada didUpdateWidget. Pode rodar muitas vezes: por isso nunca comece um Timer ou uma busca dentro dele.

O nascimento: sempre nessa ordem, uma vez.

A vida: a cada segundo o Timer chama o setState, e o build roda de novo.

O toque em "Trocar para pão" chamou o setState do pai (_PainelState). O pai se redesenhou e mandou um TimerForno(receita: 'Pão') novo para o mesmo lugar. O Flutter reaproveitou o State que já existia (por isso a contagem não voltou a 0) e avisou com o didUpdateWidget.

Depois do didUpdateWidget, sempre vem um build, agora com "Pão".
dispose
A morte: o toque em "Desligar o timer" tirou o TimerForno da árvore (o if (_ligado) ficou falso). O dispose cancelou o Timer, e nenhum build aparece depois dele.
E se ligar o timer de novo?

Um TimerForno novo entra na árvore com um State novo: initState, didChangeDependencies e build: 0 s de novo. O State antigo morreu no dispose e não volta.

2. O mapa do ciclo de vida

       o widget entra na tela
                │
          createState()
                │
           initState()              ← começar: Timer, busca, controlador
                │
      didChangeDependencies()
                │
     ┌────────► build() ◄─────────────┐
     │                                │
 setState()                   didUpdateWidget()
 (o próprio State)            (o pai mandou um widget novo)
                │
       o widget sai da tela
                │
            dispose()               ← terminar: cancelar, fechar, soltar
MétodoQuantas vezesUse paraNão use para
initState1Começar Timer, busca, controladores (TextEditingController)Ler o tema ou o MediaQuery (use o didChangeDependencies ou o build)
didChangeDependencies1 ou maisReagir a mudanças do que vem de cima (tema, InheritedWidget)Trabalho pesado sem necessidade
buildMuitasMontar a tela com o estado atualComeçar Timer, buscas, setState
didUpdateWidget0 ou maisReagir a parâmetros novos do pai (comparar oldWidget e widget)—
dispose1Cancelar Timer, fechar controladores e assinaturasChamar setState

3. O mounted: "ainda estou na tela?"

Todo State tem uma propriedade mounted ("montado"): true do initState até o dispose, e false depois. Ela é útil depois de uma espera, quando o widget pode ter saído da tela enquanto você esperava (a pessoa voltou para a tela anterior, por exemplo):

Future<void> _buscar() async {
  final preco = await buscarPrecoNaInternet();
  if (!mounted) return; // saiu da tela durante a espera: não mexe em nada
  setState(() => _preco = preco);
}

(O buscarPrecoNaInternet é ilustrativo; a busca de verdade está na aula Buscando Dados na Internet.)

Formas diferentes: onde começar as coisas

OndeFunciona?Por quê
No initStateSim: o certoRoda uma vez, quando o State nasce
Num botão ("Começar")SimQuando a coisa só deve começar a pedido; guarde o Timer num campo para cancelar no dispose
No buildNãoCada build criaria um Timer novo: um a cada segundo, todos somando juntos
No construtor do widgetNãoO widget é recriado a cada build do pai, e não tem setState

Quando dá errado

Esqueceu de cancelar o Timer no dispose

A Ana apagou a linha _timer?.cancel();:

  @override
  void dispose() {
    debugPrint('dispose');
    super.dispose();
  }

Ela abriu o app, tocou em "Desligar o timer" e esperou. A tela ficou igual à da terceira foto (os botões, sem o timer), mas o console:

[erro na página] setState() called after dispose(): _TimerFornoState#c7668(lifecycle state: defunct, not mounted)
This error happens if you call setState() on a State object for a widget that no longer appears in the widget tree (e.g., whose parent widget no longer includes the widget in its build). This error can occur when code calls setState() from a timer, from an animation callback, or after an asynchronous operation (such as an awaited network request or other Future) completes after the widget has been removed from the tree.
The preferred solution is to cancel the timer or stop listening to the animation in the dispose() callback. Another solution is to check the "mounted" property of this object before calling setState() to ensure the object is still in the tree.
This error might indicate a memory leak if setState() is being called because another object is retaining a reference to this State object after it has been removed from the tree. To avoid memory leaks, consider breaking the reference to this object during dispose().
« … e a mesma mensagem de novo a cada segundo

Linha por linha:

setState() called after dispose(): _TimerFornoState#c7668(lifecycle state: defunct, not mounted)
"setState() chamado depois do dispose()." O estado está defunct ("morto") e not mounted (fora da tela). O #c7668 é um número de identificação que muda a cada execução. O [erro na página] no começo é a marca do console do navegador do lab para um erro que ninguém tratou.
This error happens if you call setState() on a State object for a widget that no longer appears in the widget tree…
"Este erro acontece quando você chama setState() num State cujo widget não está mais na árvore." E a mensagem dá os suspeitos de sempre: um timer, uma animação ou uma espera (await) que terminou depois que o widget saiu.
The preferred solution is to cancel the timer … in the dispose() callback. Another solution is to check the "mounted" property…
As duas soluções: cancelar o timer no dispose() (a preferida) ou conferir o mounted antes do setState.
This error might indicate a memory leak…
"Pode ser um vazamento de memória": o Timer continua vivo, segurando o State morto, e o app gasta memória e bateria à toa.

O analisador do Dart até deixa uma pista antes de o app rodar: sem o cancel(), o campo _timer recebe um valor mas nunca é lido, e o dart analyze do lab avisa The value of the field '_timer' isn't used. [unused_field] ("o valor do campo _timer não é usado"). Como consertar: no dispose, cancele tudo o que o initState começou: _timer?.cancel();, antes do super.dispose();.

Esqueceu o super.initState() ou o super.dispose()

O Flutter também faz o trabalho dele nesses métodos; por isso eles são marcados com @mustCallSuper ("tem de chamar o super"). Sem a chamada, o analisador do editor sublinha o método com um aviso. Regra fácil: no initState, o super vem primeiro; no dispose, por último.

Referência rápida

EscritaO que faz
@override void initState() { super.initState(); … }Começa as coisas; roda uma vez
@override void didUpdateWidget(X oldWidget) { super.didUpdateWidget(oldWidget); … }O pai mandou parâmetros novos
@override void dispose() { …; super.dispose(); }Termina as coisas; roda uma vez
Timer.periodic(Duration(seconds: 1), (_) { … })Chama a função a cada segundo (import 'dart:async';)
_timer?.cancel()Para o Timer
if (!mounted) return;Depois de uma espera, sai se o widget não está mais na tela

2. Onde se cancela um Timer criado no initState?

3. O pai chamou setState e mandou um TimerForno(receita: 'Pão') no lugar do TimerForno(receita: 'Bolo'). O que roda no State do timer?

4. Por que não se deve começar um Timer dentro do build?

Resumo

  • O State nasce com initState → didChangeDependencies → build, vive com um build a cada setState ou didUpdateWidget, e morre com o dispose.
  • initState e dispose rodam uma vez cada: comece as coisas num e termine-as no outro.
  • didUpdateWidget avisa que o pai mandou parâmetros novos; o State é reaproveitado (a contagem continua).
  • O build roda muitas vezes: só monte a tela nele.
  • Esquecer o cancel() no dispose dá setState() called after dispose() e vazamento de memória. Depois de uma espera, confira o mounted.
